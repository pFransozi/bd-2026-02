Aula 07 · material de aprofundamento

Manipular dados é transformar o estado do banco sem romper suas regras

Na aula principal usamos INSERT, UPDATE e DELETE e observamos restrições sendo aceitas ou rejeitadas pelo SQLite. Neste aprofundamento vamos desacelerar esse percurso: primeiro separar estrutura e estado, depois entender cada operação de manipulação, em seguida observar como as constraints validam as mudanças e, por fim, compreender as consequências das referências entre tabelas.

Leitura conceitualDMLIntegridadeConstraintsSQLite
Pergunta central
O que significa dizer que uma alteração de dados é válida?

Uma operação não é correta apenas porque sua sintaxe foi aceita. O novo estado do banco também precisa respeitar as regras definidas para o domínio.

1 · Estrutura e estado

Primeiro precisamos separar a estrutura do banco dos dados que estão dentro dela

Essa distinção ajuda a entender por que a Aula 06 trabalhou com DDL e por que a Aula 07 passa a trabalhar com DML. A estrutura permanece relativamente estável; os dados mudam o tempo todo.

O esquema funciona como a definição do que pode ser armazenado

Quando criamos a tabela RESERVA, definimos que uma reserva possui um identificador, um usuário, uma sala, uma data, um horário e uma situação. Também definimos regras, como a obrigatoriedade de certos valores e a necessidade de que usuário e sala já existam.

Essas decisões formam o esquema. O esquema não representa uma reserva específica. Ele descreve a forma que qualquer reserva válida deverá possuir.

Exemplo de estrutura já definida
RESERVA(
    id_reserva,
    id_usuario,
    id_sala,
    data,
    hora_inicio,
    situacao
)

A instância é o conteúdo que existe em determinado momento

Depois que a estrutura existe, começamos a armazenar ocorrências concretas. Uma linha pode representar, por exemplo, uma reserva feita pelo usuário 17 para a sala 204 em determinada data e horário.

O conjunto de todas as linhas presentes naquele momento forma a instância atual da relação. Se inserirmos uma nova reserva, a estrutura continua sendo RESERVA, mas sua instância mudou.

Esquema

A forma permanece

Define colunas, tipos, chaves e restrições. Responde à pergunta: como uma reserva válida deve ser representada?

Instância

O conteúdo muda

É o conjunto atual de linhas. Responde à pergunta: quais reservas existem neste momento?

É aqui que DML entra

Os comandos de manipulação não redefinem o significado de uma relação. Eles modificam as ocorrências armazenadas nela.

Quando usamos INSERT, acrescentamos uma nova ocorrência. Quando usamos UPDATE, produzimos uma nova versão de uma ocorrência já existente. Quando usamos DELETE, removemos uma ocorrência.

1Estado inicial

O banco possui um conjunto de linhas que já respeitam as restrições.

2Comando DML

Uma operação tenta inserir, alterar ou remover dados.

3Validação

O SGBD verifica as restrições envolvidas na operação.

4Novo estado

Se as regras continuam satisfeitas, a mudança é aceita.

Uma forma simples de pensar

DDL define o formato do recipiente. DML modifica o conteúdo que está dentro dele. As constraints determinam quais conteúdos são permitidos.

Estado válido não significa apenas "SQL sem erro de sintaxe"

Um comando pode estar escrito corretamente e ainda assim ser rejeitado. Isso acontece quando a operação tentaria produzir um estado incompatível com alguma regra do banco.

Por exemplo, INSERT INTO sala ... id_bloco = 99 pode estar sintaticamente correto. Se o bloco 99 não existe e existe uma chave estrangeira para BLOCO, o novo estado seria inválido. O SGBD então rejeita a mudança.

Estado válido A→ operação →verificação das regras→Estado válido B

2 · DML como transformação de estado

INSERT, UPDATE e DELETE são três maneiras diferentes de modificar os fatos armazenados

Os três comandos pertencem ao mesmo momento do trabalho com o banco, mas cada um produz uma transformação diferente sobre uma relação.

INSERT

Cria uma nova linha. A pergunta é: essa nova ocorrência pode existir sem violar as regras?

UPDATE

Altera valores de linhas que já existem. A pergunta é: depois da alteração, essas ocorrências continuam válidas?

DELETE

Remove linhas. A pergunta é: a remoção deixa alguma referência ou regra quebrada?

INSERT: acrescentar uma nova ocorrência

Quando executamos um INSERT, estamos propondo um novo fato para o banco. O SGBD não simplesmente acrescenta a linha. Antes de confirmar a operação, ele verifica as restrições que se aplicam à nova ocorrência.

Inserção de uma nova reserva
INSERT INTO reserva (
    id_reserva, id_usuario, id_sala, data, hora_inicio
)
VALUES (
    1, 17, 204, '2026-09-18', '18:30'
);

Esse comando precisa passar por várias perguntas implícitas:

  • id_reserva = 1 já existe?
  • o usuário 17 existe?
  • a sala 204 existe?
  • data e horário possuem valores aceitos pela estrutura?
  • já existe outra reserva para a mesma sala, data e horário quando essa combinação é UNIQUE?
  • o valor de situacao foi omitido? Se sim, existe um DEFAULT?

Se todas as condições relevantes forem satisfeitas, a nova tupla passa a fazer parte da relação.

UPDATE: produzir uma nova versão das linhas selecionadas

UPDATE não "edita uma célula" isoladamente como em uma planilha. Ele seleciona um conjunto de linhas e produz novos valores para os atributos indicados.

Atualização de uma reserva
UPDATE reserva
SET situacao = 'cancelada'
WHERE id_reserva = 1;

Podemos ler esse comando em três partes:

1Relação alvo

UPDATE reserva indica qual relação será modificada.

2Novo valor

SET situacao = 'cancelada' define a alteração.

3Conjunto alvo

WHERE id_reserva = 1 seleciona quais linhas serão atingidas.

4Nova validação

O valor resultante precisa continuar atendendo às constraints.

Se trocássemos 'cancelada' por 'aguardando', e o CHECK permitisse apenas ativa, cancelada e concluida, a atualização seria rejeitada.

DELETE: remover uma ocorrência inteira

DELETE remove linhas completas. Ele não remove apenas uma coluna da estrutura e também não elimina a tabela. Esses outros efeitos pertencem a operações diferentes.

Remoção de uma ocorrência
DELETE FROM telefone_usuario
WHERE id_usuario = 42
  AND telefone = '41984327710';

Aqui a condição identifica uma combinação específica de usuário e telefone. Se ela corresponder a uma linha, essa ocorrência é removida da relação.

DELETE não é DROP

DML

DELETE FROM sala;

Remove linhas da tabela SALA, mas a estrutura da tabela continua existindo.

DDL

DROP TABLE sala;

Remove a própria tabela como objeto do esquema. A estrutura deixa de existir.

E o SELECT?

Neste material, tratamos SELECT como comando de consulta. Ele não modifica o estado do banco, mas é essencial para trabalhar com DML de maneira consciente.

Antes de alterar ou excluir, o SELECT permite verificar quais linhas satisfazem a condição. Depois da operação, ele permite observar o novo estado.

SELECT→entender o estado→UPDATE/DELETE→SELECT
Por isso usamos SELECT junto com DML na aula

Não porque SELECT altere dados, mas porque ele nos permite enxergar o conjunto que será transformado e verificar o resultado depois da mudança.

3 · Integridade

Integridade é a ideia de manter o banco coerente com as regras do domínio

Uma constraint é uma forma de registrar no próprio banco uma condição que deve permanecer verdadeira. Quando uma operação tenta quebrar essa condição, o SGBD deve impedir a mudança.

Integridade de entidade: cada ocorrência precisa continuar identificável

No modelo relacional, precisamos distinguir uma tupla das demais. A chave primária cumpre esse papel.

Se duas linhas de USUARIO tivessem o mesmo id_usuario, não conseguiríamos mais afirmar com segurança qual usuário uma reserva está referenciando. Por isso, a chave primária exige unicidade.

Regra de identidade
id_usuario INTEGER PRIMARY KEY

Em termos simples: duas ocorrências diferentes não podem compartilhar a mesma identidade primária.

Integridade de domínio: nem todo valor faz sentido para todo atributo

Um atributo representa uma propriedade específica. Portanto, seus valores precisam pertencer a um conjunto coerente com essa propriedade.

Na relação SALA, uma capacidade negativa não representa um estado válido. Na relação RESERVA, uma situação como 'aguardando' também pode ser inválida se o domínio definido permitir apenas três valores.

Faixa válida

Capacidade

CHECK (capacidade > 0) impede valores incompatíveis com a ideia de capacidade da sala.

Conjunto válido

Situação

CHECK (situacao IN (...)) limita o atributo aos estados reconhecidos pelo sistema.

Integridade referencial: referências precisam apontar para algo que existe

Uma chave estrangeira não é apenas uma coluna com um número. Ela representa uma ligação entre ocorrências de relações diferentes.

Se RESERVA.id_usuario = 17, esse valor significa "esta reserva pertence ao usuário identificado por 17". Se nenhum usuário 17 existe, a referência perde o significado.

Referência declarada
FOREIGN KEY (id_usuario)
    REFERENCES usuario(id_usuario)

As principais constraints da aula atuam em pontos diferentes

ConstruçãoPergunta que ela respondeExemplo na aula
PRIMARY KEYComo distinguir cada ocorrência?id_reserva identifica cada reserva.
FOREIGN KEYEssa referência aponta para uma ocorrência existente?id_sala precisa corresponder a uma sala válida.
NOT NULLEsse valor pode estar ausente?Uma sala precisa possuir nome e capacidade.
UNIQUEEsse valor ou combinação pode se repetir?A mesma sala não pode receber duas reservas na mesma data e horário.
CHECKEsse valor pertence ao conjunto considerado válido?Capacidade positiva e situação pertencente ao conjunto definido.
DEFAULTQual valor deve ser usado quando o atributo for omitido?Uma nova reserva recebe 'ativa' por padrão.

NOT NULL não significa "valor correto"

NOT NULL verifica apenas se existe algum valor. Ele não verifica se o valor faz sentido.

Por exemplo, uma capacidade de -3 não é nula. Portanto, NOT NULL sozinho aceitaria esse valor. Precisamos de CHECK para expressar a regra adicional.

UNIQUE pode envolver mais de uma coluna

Na aula, a regra de agenda não é "a data deve ser única" nem "o horário deve ser único". O que não pode se repetir é a combinação de sala + data + horário.

Unicidade composta
UNIQUE (id_sala, data, hora_inicio)

Isso permite várias reservas na mesma data, desde que sejam em salas ou horários diferentes.

DEFAULT fornece um valor, mas não valida todos os valores possíveis

Esse ponto merece atenção. DEFAULT é aplicado quando um valor é omitido na inserção. Ele não impede que alguém informe explicitamente outro valor.

Duas funções diferentes
situacao TEXT NOT NULL DEFAULT 'ativa'
    CHECK (situacao IN ('ativa', 'cancelada', 'concluida'))

Nessa definição:

  • DEFAULT 'ativa' escolhe o valor inicial quando situacao não é informada;
  • NOT NULL impede ausência de valor;
  • CHECK limita quais valores são aceitos.
Constraints trabalham em conjunto

Uma coluna pode precisar de várias regras porque cada constraint responde a um problema diferente.

Uma operação rejeitada pode indicar que o banco funcionou corretamente

Se tentamos inserir uma sala com bloco inexistente e recebemos uma violação de chave estrangeira, o SGBD impediu que uma referência sem significado fosse armazenada.

O mesmo ocorre quando uma PK duplicada, um CHECK inválido ou uma combinação UNIQUE repetida é rejeitada.

Nesses casos, a mensagem de erro não significa que a integridade falhou. Significa justamente que a integridade foi preservada.

4 · Integridade referencial e ações de exclusão

Uma exclusão pode começar em uma tabela e produzir consequências em outra

Quando existem chaves estrangeiras, remover uma linha referenciada exige decidir o que deve acontecer com as linhas que dependem dela.

Primeiro, identifique os dois lados da referência

Considere a relação entre USUARIO e TELEFONE_USUARIO.

USUARIO.id_usuario← referência ←TELEFONE_USUARIO.id_usuario

USUARIO contém a chave referenciada. TELEFONE_USUARIO contém a chave estrangeira. Isso significa que a existência de uma linha de telefone depende de uma ocorrência de usuário.

O problema aparece quando a linha referenciada é removida

Imagine que o usuário 17 possui dois telefones cadastrados. Se apagarmos o usuário 17, o que deve acontecer com esses telefones?

Existem diferentes respostas possíveis. A escolha correta depende do significado do domínio.

RESTRICT

Não permita a exclusão

Enquanto existirem linhas dependentes, a linha referenciada permanece protegida. Primeiro é preciso resolver as dependências.

CASCADE

Remova também as dependências

A exclusão da linha referenciada provoca a remoção automática das linhas que dependem dela.

SET NULL

Mantenha a linha sem referência

A linha dependente permanece, mas a FK passa a ser nula. Isso só faz sentido se a coluna aceitar NULL.

Por que TELEFONE_USUARIO usa ON DELETE CASCADE?

Na estrutura da aula, TELEFONE_USUARIO representa telefones associados a um usuário. A linha (17, '41987651223') não representa um telefone independente do usuário; ela representa um telefone do usuário 17.

Se o usuário deixar de existir, manter essa linha produziria um fato sem proprietário. Por isso, a aula usa:

Dependência forte
FOREIGN KEY (id_usuario)
    REFERENCES usuario(id_usuario)
    ON DELETE CASCADE

Ao excluir o usuário, os telefones associados também são removidos.

Por que RESERVA usa ON DELETE RESTRICT?

RESERVA possui um papel diferente. Uma reserva registra um fato do sistema que envolve usuário, sala, data e horário. Apagar automaticamente reservas porque um usuário foi excluído pode destruir informação que o sistema ainda precisa preservar.

Por isso, na aula adotamos RESTRICT. Se houver uma reserva apontando para o usuário, a exclusão do usuário é bloqueada.

Proteção da referência
FOREIGN KEY (id_usuario)
    REFERENCES usuario(id_usuario)
    ON DELETE RESTRICT

CASCADE não é "melhor" ou "pior" que RESTRICT

São comportamentos diferentes. A escolha depende do que a relação dependente representa.

Relação dependenteSe o pai for excluído...Interpretação
TELEFONE_USUARIOCASCADEO telefone deixa de existir como vínculo porque seu proprietário foi removido.
RESERVA em relação a USUARIORESTRICTO usuário não pode ser removido enquanto uma reserva ainda depende dele.
RESERVA em relação a SALARESTRICTA sala não pode desaparecer deixando reservas com referência quebrada.

E onde SET NULL faria sentido?

SET NULL é adequado quando a linha dependente ainda faz sentido mesmo sem a referência original.

Por exemplo, em outro domínio, poderíamos manter um registro histórico e permitir que uma referência opcional para um responsável seja removida. Para isso, a coluna da FK precisaria aceitar NULL.

No nosso caso de RESERVA, id_usuario e id_sala são obrigatórios. Portanto, SET NULL entraria em conflito com essa decisão.

A ação referencial traduz uma regra do domínio

Escolher CASCADE, RESTRICT ou SET NULL significa decidir o que deve acontecer com fatos dependentes quando a ocorrência referenciada deixa de existir.

No SQLite, declarar a FK e fiscalizar a FK são duas etapas relacionadas

A constraint é escrita na definição da tabela, mas a conexão usada na aula também executa PRAGMA foreign_keys = ON.

SQLite
PRAGMA foreign_keys = ON;

Esse comando não cria as chaves estrangeiras. Ele ativa a fiscalização das FKs declaradas para aquela conexão.

5 · O predicado define o alcance da mudança

UPDATE e DELETE trabalham com conjuntos de linhas

Essa é uma mudança importante de raciocínio: SQL não precisa receber uma linha de cada vez. Uma única instrução pode atingir nenhuma, uma ou muitas ocorrências.

WHERE funciona como um filtro sobre as linhas

A cláusula WHERE contém uma condição lógica. Cada linha é avaliada em relação a essa condição. As linhas que satisfazem o predicado entram no conjunto alvo da operação.

Predicado sobre uma chave
WHERE id_reserva = 1

Como id_reserva é chave primária, no máximo uma linha pode satisfazer essa condição.

Predicado sobre um valor comum
WHERE situacao = 'ativa'

Nesse caso, várias linhas podem satisfazer a condição. Portanto, um UPDATE com esse predicado pode modificar várias reservas ao mesmo tempo.

Condição sobre chave

Alcance previsivelmente pequeno

A unicidade da chave garante que o predicado alcance no máximo uma linha.

Condição não exclusiva

Alcance potencialmente grande

Qualquer quantidade de linhas pode compartilhar o mesmo valor e entrar no conjunto alvo.

Sem WHERE, nenhuma linha é filtrada

Observe a diferença:

Com filtro
UPDATE reserva
SET situacao = 'cancelada'
WHERE id_reserva = 1;
Sem filtro
UPDATE reserva
SET situacao = 'cancelada';

O segundo comando não contém erro de sintaxe. Ele significa: aplique a nova situação a todas as linhas de RESERVA.

Por isso "esquecer o WHERE" é tão perigoso

O SGBD não conhece a intenção humana por trás do comando. Ele executa exatamente a transformação descrita.

Se a intenção era alterar uma reserva e o predicado seleciona todas, o banco não possui informação suficiente para adivinhar que o comando estava amplo demais.

A estratégia SELECT → conferir → modificar reduz esse risco

Antes de usar UPDATE ou DELETE, podemos aplicar a mesma condição em um SELECT.

Primeiro observe
SELECT *
FROM reserva
WHERE id_reserva = 1;

Se o resultado contém exatamente a ocorrência esperada, podemos reutilizar o mesmo predicado na operação de modificação.

1Definir a intenção

Qual ocorrência ou conjunto realmente precisa ser alterado?

2Escrever o predicado

Transforme essa intenção em uma condição lógica.

3Conferir com SELECT

Veja quais linhas satisfazem a condição no estado atual.

4Executar e conferir

Aplique UPDATE/DELETE e consulte novamente.

WHERE não garante que a condição está correta

Ele apenas limita o conjunto segundo a expressão escrita. Um predicado incorreto ainda pode selecionar linhas erradas. A conferência continua necessária.

6 · Banco e aplicação

A aplicação pode orientar o usuário; o banco precisa preservar os dados

Em um sistema real, regras podem aparecer em diferentes camadas. O ponto importante é entender que validação de interface e integridade do banco possuem objetivos diferentes.

A aplicação trabalha perto da interação com o usuário

Uma interface pode impedir que o usuário digite letras em um campo numérico, exigir preenchimento, exibir opções de situação em uma lista e pedir confirmação antes de uma exclusão.

Essas validações melhoram a experiência porque evitam operações obviamente incorretas antes mesmo de chegar ao banco.

Exemplo

Seleção da situação

A interface pode apresentar apenas três opções: ativa, cancelada e concluída. Assim, o usuário nem vê a opção "aguardando".

Mas a aplicação não é o único caminho até o banco

Dados podem ser modificados por scripts, integrações, rotinas administrativas, importações ou outra versão da aplicação.

Se uma regra fundamental existir apenas na tela, outro caminho de escrita pode ignorá-la.

O SGBD atua no ponto onde os dados são persistidos

Quando uma constraint está no banco, qualquer operação que tente produzir um estado inválido precisa enfrentar a mesma regra.

Aplicação

Antecipar e explicar

Ajuda o usuário a fornecer dados válidos, mostra mensagens compreensíveis e organiza o fluxo da operação.

Banco de dados

Preservar invariantes

Mantém regras estruturais essenciais independentemente de qual aplicação, script ou usuário enviou o comando.

As duas camadas podem representar a mesma regra por motivos diferentes

Considere a capacidade da sala.

  • a aplicação pode impedir a digitação de números menores ou iguais a zero;
  • o banco pode manter CHECK (capacidade > 0).

Isso não é necessariamente duplicação inútil. A interface melhora a interação; a constraint protege o estado persistido.

Nem toda regra cabe facilmente em uma constraint simples

Algumas regras dependem de várias linhas, de tempo, de processos da aplicação ou de decisões mais complexas. Por isso, o projeto precisa decidir onde cada regra será garantida.

Nesta aula trabalhamos principalmente com regras que podem ser expressas diretamente por PK, FK, NOT NULL, UNIQUE, CHECK, DEFAULT e ações referenciais.

Princípio útil

Quanto mais central uma regra for para a consistência dos dados, menos ela deve depender apenas de uma interface específica.

Síntese conceitual

Manipular dados é propor mudanças; integridade decide quais mudanças podem permanecer

A Aula 07 deixa de olhar apenas para a estrutura e passa a observar o comportamento do banco quando seu estado é alterado.

Estado

O esquema define a forma. A instância representa os dados que existem agora.

DML

INSERT, UPDATE e DELETE transformam o conjunto atual de tuplas.

Integridade

As constraints impedem que uma transformação produza estados incompatíveis com as regras declaradas.

O percurso desta aula pode ser lido assim

Estrutura pronta→estado atual→operação DML→constraints→novo estado válido

Quatro ideias para guardar

1

DML muda dados

Não redefine a estrutura do banco; modifica a instância atual.

2

SQL opera sobre conjuntos

UPDATE e DELETE podem atingir nenhuma, uma ou muitas linhas.

3

Erro pode ser proteção

Uma operação rejeitada por uma constraint pode indicar que a integridade foi preservada.

4

FK expressa dependência

Ações como CASCADE e RESTRICT registram consequências da exclusão de ocorrências referenciadas.
