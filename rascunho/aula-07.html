Aula 07 · Manipulação de dados e integridade

Agora o banco começa a receber dados

Na Aula 06 transformamos o modelo normalizado em tabelas do PostgreSQL. Nesta aula vamos inserir, alterar e excluir dados e observar o que acontece quando uma operação tenta violar as regras que construímos desde a modelagem.

INSERTUPDATEDELETEPRIMARY KEYFOREIGN KEYCHECKUNIQUEDEFAULT
Pergunta-guia
Criar as tabelas é suficiente para garantir que os dados armazenados estejam corretos?

Visão da aula

O que vamos desenvolver

O foco não será decorar comandos. Vamos executar operações, prever seus efeitos e interpretar por que o PostgreSQL aceita ou rejeita cada tentativa.

Objetivos de aprendizagem

  • Inserir registros com INSERT.
  • Alterar registros com UPDATE e delimitar mudanças com WHERE.
  • Excluir registros com DELETE e analisar referências existentes.
  • Interpretar violações de PK, FK e NOT NULL.
  • Aplicar e interpretar CHECK, DEFAULT e UNIQUE.
  • Distinguir integridade de entidade, domínio e referencial.

Competências mobilizadas

  • C2 · H6/H8: aplicar procedimentos de manipulação que preservem consistência.
  • C3 · H9: identificar regras do domínio que precisam ser garantidas pela estrutura.
  • C10 · H34: explicar comandos, resultados e mensagens de erro com linguagem técnica.
  • C11 · H36/H38: aplicar boas práticas na manutenção dos dados.

INSERT

Adiciona uma nova ocorrência a uma tabela.

UPDATE

Altera valores de ocorrências já armazenadas.

3 · INSERT

Comece pelas tabelas que não dependem de outras

A ordem das inserções não é um detalhe administrativo. Quando uma tabela possui chave estrangeira, o registro referenciado precisa existir antes.

Primeiros blocos

Inserção simples
INSERT INTO bloco (id_bloco, nome_bloco)
VALUES (1, 'Bloco A');
Vários registros
INSERT INTO bloco (id_bloco, nome_bloco)
VALUES
    (2, 'Bloco B'),
    (3, 'Bloco C'),
    (4, 'Bloco D');
INSERT INTO blocoindica em qual tabela queremos inserir uma ocorrência.
(id_bloco, nome_bloco)indica quais colunas receberão valores.
VALUES (...)contém os valores que serão armazenados.

Depois, uma sala

Sala vinculada a um bloco existente
INSERT INTO sala (
    id_sala,
    nome,
    capacidade,
    id_bloco
)
VALUES (
    204,
    'Sala Ipê',
    6,
    2
);

A sala pode ser inserida porque id_bloco = 2 já existe na tabela bloco.

Usuários e telefones

Usuários
INSERT INTO usuario (id_usuario, nome)
VALUES
    (17, 'Marina Lopes'),
    (42, 'Gustavo Neri'),
    (8, 'Larissa Moura');
Telefones
INSERT INTO telefone_usuario (id_usuario, telefone)
VALUES
    (17, '41987651223'),
    (17, '41991128080'),
    (42, '41984327710'),
    (8, '41995543901');

A decisão da modelagem aparece agora nos dados: os dois telefones de Marina não estão armazenados como uma lista dentro de uma célula. Cada telefone é uma ocorrência própria ligada ao usuário.

Regra prática

Insira primeiro as ocorrências independentes; depois, as ocorrências que dependem delas por chave estrangeira.

Antes de executar

Se uma sala aponta para id_bloco = 99 e esse bloco não existe, o comando deveria ser aceito?

4 · Aprender com as recusas do SGBD

Uma mensagem de erro também explica uma regra do banco

Em vez de tratar um erro apenas como “o comando não funcionou”, pergunte qual regra impediu a operação e por que essa regra existe.

Integridade de entidade

PRIMARY KEY

Garante que cada ocorrência possa ser identificada de forma única.

Integridade referencial

FOREIGN KEY

Garante que uma referência a outra tabela aponte para uma ocorrência existente.

Integridade de domínio

tipo · NOT NULL · CHECK

Limita os valores de acordo com características e regras do domínio.

Teste A · chave estrangeira inválida

Usuário inexistente
INSERT INTO telefone_usuario (id_usuario, telefone)
VALUES (999, '41999999999');

O comando referencia usuario.id_usuario = 999. Se esse usuário não existe, a chave estrangeira impede que o telefone fique “solto” no banco.

Teste B · chave primária duplicada

Identificador já utilizado
INSERT INTO usuario (id_usuario, nome)
VALUES (17, 'Outra pessoa');

id_usuario = 17 já identifica Marina Lopes. Uma segunda ocorrência com a mesma PK impediria que o banco distinguisse unicamente os usuários.

Teste C · valor obrigatório ausente

Violação de NOT NULL
INSERT INTO usuario (id_usuario, nome)
VALUES (90, NULL);

A coluna foi definida como nome VARCHAR(120) NOT NULL. Portanto, o próprio banco impede a criação de uma ocorrência sem nome.

Leia o erro como diagnóstico

Uma violação de restrição informa que o SGBD está cumprindo uma decisão estrutural. O problema não é necessariamente a sintaxe do SQL; pode ser o dado proposto.

Pergunta útil

O comando está sintaticamente incorreto ou os valores não satisfazem as regras declaradas para a tabela?

5 · Regras além de PK e FK

CHECK, DEFAULT e UNIQUE tornam regras do domínio executáveis

Nem toda regra é uma chave. O PostgreSQL também pode verificar condições, preencher valores padrão e impedir repetições que o domínio considera inválidas.

CHECK · um valor precisa satisfazer uma condição

Capacidade precisa ser positiva
ALTER TABLE sala
ADD CONSTRAINT chk_sala_capacidade
CHECK (capacidade > 0);
Teste inválido
INSERT INTO sala (
    id_sala, nome,
    capacidade, id_bloco
)
VALUES (
    500,
    'Sala Teste',
    -5,
    1
);
Sintaxe correta não significa dado válido

O comando pode estar escrito corretamente e ainda assim ser rejeitado porque -5 viola uma regra definida para o domínio da capacidade.

CHECK · situações permitidas para uma reserva

Conjunto permitido
ALTER TABLE reserva
ADD CONSTRAINT chk_reserva_situacao
CHECK (
    situacao IN (
        'ativa',
        'cancelada',
        'concluida'
    )
);

DEFAULT · o valor utilizado quando nada é informado

Situação inicial padrão
ALTER TABLE reserva
ALTER COLUMN situacao
SET DEFAULT 'ativa';
Omitindo a situação
INSERT INTO reserva (
    id_reserva,
    id_usuario,
    id_sala,
    data,
    hora_inicio
)
VALUES (
    2,
    42,
    204,
    '2026-09-19',
    '14:00'
);
DEFAULT não significa “campo opcional”

Significa que, quando o comando não fornece explicitamente um valor, o SGBD pode utilizar o valor padrão definido para aquela coluna.

UNIQUE · uma combinação não pode se repetir

Exemplo didático de unicidade de horário
ALTER TABLE reserva
ADD CONSTRAINT uq_reserva_horario
UNIQUE (id_sala, data, hora_inicio);

Com essa regra, dois registros não podem utilizar a mesma sala, data e horário.

Atenção à regra real do domínio

Esse UNIQUE só é adequado se o domínio realmente proibir uma segunda ocorrência para aquele horário. Se uma reserva cancelada liberar o horário e o sistema mantiver o cancelamento como histórico, uma restrição simples sobre sala, data e hora pode ser insuficiente. A restrição deve representar a regra real, não apenas parecer conveniente.

RestriçãoPergunta que ela respondeExemplo nesta aula
PRIMARY KEYComo identifico unicamente esta ocorrência?reserva.id_reserva
FOREIGN KEYA referência aponta para algo que existe?reserva.id_usuario → usuario.id_usuario
NOT NULLEste dado pode ficar ausente?usuario.nome
CHECKEste valor satisfaz uma condição?capacidade > 0
DEFAULTQual valor usar quando nenhum for informado?situacao = 'ativa'
UNIQUEEste valor ou combinação pode se repetir?sala + data + hora

6 · UPDATE

Os dados mudam — e o WHERE define o alcance da mudança

Uma reserva que estava ativa pode ser cancelada. O comando UPDATE altera ocorrências existentes; a cláusula WHERE determina quais ocorrências serão afetadas.

Alteração delimitada
UPDATE reserva
SET situacao = 'cancelada'
WHERE id_reserva = 10;
UPDATE reservaindica a tabela que será modificada.
SET situacao = 'cancelada'define o novo valor.
WHERE id_reserva = 10limita a operação à reserva desejada.

Agora remova o WHERE mentalmente

Comando válido, efeito perigoso
UPDATE reserva
SET situacao = 'cancelada';

Esse comando não é um erro de sintaxe. Ele faz exatamente o que foi escrito: altera todas as linhas da tabela.

Uma rotina segura

Antes de um UPDATE importante, verifique com uma consulta quais linhas satisfazem a condição:

Conferência antes da alteração
SELECT *
FROM reserva
WHERE id_reserva = 10;

Nesta aula o SELECT aparece apenas como ferramenta de conferência. As consultas serão aprofundadas na próxima aula.

UPDATE sem WHERE

O perigo está justamente no fato de o comando ser válido. O SGBD não sabe que você pretendia alterar apenas uma linha.

Antes de executar

Quantas linhas serão afetadas pela condição utilizada?

7 · DELETE e integridade referencial

Excluir uma linha pode afetar outras partes do modelo

Quando uma ocorrência é referenciada por outra tabela, apagar não é uma decisão local. Precisamos decidir o que deve acontecer com as dependências.

Exclusão delimitada
DELETE FROM reserva
WHERE id_reserva = 10;
Sem WHERE
DELETE FROM reserva;

Assim como no UPDATE, a ausência de WHERE significa que todas as ocorrências são alvo da operação.

O que acontece se o usuário ainda possuir reservas?

Teste de integridade referencial
DELETE FROM usuario
WHERE id_usuario = 17;

Se houver uma reserva que referencia o usuário 17, a chave estrangeira impede que a referência fique apontando para uma ocorrência inexistente, salvo se uma política de exclusão tiver sido explicitamente definida.

Políticas possíveis de ON DELETE

RESTRICT / NO ACTION

não excluir

Impede a remoção enquanto existirem registros dependentes.

CASCADE

excluir dependentes

Remove também as ocorrências que referenciam a ocorrência apagada.

SET NULL

FK = NULL

Mantém os registros dependentes, mas remove a referência, desde que a coluna aceite NULL.

Exemplo de definição com CASCADE
FOREIGN KEY (id_usuario)
    REFERENCES usuario(id_usuario)
    ON DELETE CASCADE
Não existe uma política universal

ON DELETE CASCADE não é uma “melhoria automática”. A escolha precisa representar o significado do relacionamento.

Compare dois casos

Apagar os telefones quando um usuário é removido pode fazer sentido. Mas apagar automaticamente todo o histórico de reservas desse usuário representa corretamente o domínio?

Prática em dupla

Construa uma pequena história no banco

Represente a seguinte situação sem receber os comandos prontos:

Camila foi cadastrada como usuária. Ela possui dois telefones. Uma nova sala chamada Sala Pinheiro, com capacidade para oito pessoas, foi cadastrada no Bloco B. Camila realizou uma reserva dessa sala para 30/09/2026 às 19h. Posteriormente, a reserva foi cancelada.

  1. Cadastre Camila.
  2. Cadastre seus dois telefones.
  3. Cadastre a sala.
  4. Registre a reserva.
  5. Altere a situação da reserva para cancelada.
Depois que funcionar, provoque três erros de propósito

Tente reutilizar a chave de Camila, criar uma reserva para uma sala inexistente e inserir uma situação não permitida. Em cada caso, registre a mensagem do PostgreSQL e a regra que ela representa.

Síntese

O banco não armazena apenas valores: ele também protege regras

Ao final desta aula, a estrutura criada anteriormente passa a receber dados reais, e as restrições deixam de ser apenas definições do modelo para se tornarem comportamentos observáveis do SGBD.

O que consolidamos

INSERT, UPDATE e DELETE modificam dados; PK, FK, NOT NULL, CHECK, DEFAULT e UNIQUE limitam quais estados do banco são aceitáveis.
