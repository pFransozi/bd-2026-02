Visão da aula

O que vamos desenvolver

Depois de construir e normalizar o esquema, vamos passar a manipular dados reais. A ideia é compreender os comandos de DML e, ao mesmo tempo, observar como as restrições do banco preservam as regras que surgiram durante a modelagem.

  • Diferenciar integridade de entidade, domínio e referencial.
  • Analisar os efeitos de regras de ON DELETE sobre dados relacionados.

0 · Preparando o ambiente

Como o notebook conversa com o banco de dados?

Antes de começar os comandos da aula, precisamos montar a conexão. O notebook executa Python, mas os comandos que queremos enviar ao banco são SQL. Entre esses dois lados existe um componente de conexão: o driver ou conector.

Notebook / Python→driver do banco→banco de dados→resultado

Python

É a linguagem que estamos usando no notebook para abrir a conexão, enviar comandos e receber os resultados.

Driver

É a biblioteca que faz a comunicação entre o código Python e o mecanismo de banco de dados. Cada tecnologia possui drivers próprios.

Banco

Recebe o SQL, executa a operação e devolve um resultado ou uma mensagem de erro.

No nosso ambiente, o driver já está disponível

Usaremos o módulo sqlite3, que já acompanha o Python. Por isso não precisamos instalar nenhum pacote adicional no Google Colab para começar.

Primeira célula do notebook

Crie o arquivo do banco e abra uma conexão

Se o arquivo ainda não existir, ele será criado quando a conexão for aberta. A conexão permanecerá disponível enquanto a sessão do notebook estiver ativa.

Python · conexão com o banco
import sqlite3

conexao = sqlite3.connect("reserva_salas.db")
cursor = conexao.cursor()

print("Banco conectado com sucesso!")

conexao

Representa a sessão aberta com o arquivo do banco. É por meio dela que confirmamos alterações e encerramos o acesso ao banco.

cursor

É o objeto usado para enviar comandos SQL e recuperar os resultados produzidos por esses comandos.

Chaves estrangeiras

Ative a verificação das referências

Para os testes desta aula, queremos que referências inválidas sejam realmente rejeitadas. Faça essa configuração logo depois de abrir a conexão.

Python · ativando as FKs
cursor.execute("PRAGMA foreign_keys = ON;")

cursor.execute("PRAGMA foreign_keys;")
print(cursor.fetchone())
Resultado esperado

Se aparecer (1,), a verificação de chaves estrangeiras está ativa nessa conexão. Se a conexão for recriada, essa configuração precisa ser executada novamente.

Como enviaremos SQL

O SQL vai dentro das células Python

Na página da aula mostraremos os comandos em SQL puro para destacar a linguagem. No notebook, o driver recebe esses comandos por meio do cursor.

Exemplo de execução
cursor.execute("""
INSERT INTO usuario (id_usuario, nome)
VALUES (17, 'Marina Lopes');
""")

conexao.commit()

cursor.execute(...)

Envia um comando SQL para o banco.

conexao.commit()

Confirma alterações feitas por comandos como INSERT, UPDATE e DELETE.

O arquivo do banco fica no ambiente da sessão

Se a sessão do Colab for encerrada ou reiniciada, os arquivos locais podem desaparecer. Para a aula isso é suficiente; se quisermos preservar o banco depois, podemos salvar o arquivo em outro local.

1 · Retomada

Antes de manipular dados, recupere o que já está pronto

Na Aula 06 chegamos a um ponto importante: o domínio já foi interpretado, o modelo foi transformado em relações, a estrutura foi normalizada e as tabelas foram criadas. Portanto, nesta aula não vamos começar um novo banco. Vamos continuar trabalhando sobre aquilo que já construímos.

Domínio e requisitos→MER / DER→Modelo relacional→Normalização→Estrutura pronta→Manipulação dos dados

1. O domínio disse o que existe

Identificamos usuários, salas, reservas, blocos e as regras que conectam essas informações.

2. O modelo organizou essas informações

Entidades e relacionamentos foram transformados em relações com chaves primárias, chaves estrangeiras e atributos bem definidos.

3. A estrutura já está pronta

As tabelas existem e possuem regras. Agora a pergunta deixa de ser “como criar?” e passa a ser “o que acontece quando manipulamos os dados?”.

Até aqui criamos estrutura, não ocorrências

Uma tabela pode existir perfeitamente sem possuir nenhuma linha. A definição diz quais colunas existem e quais regras devem ser respeitadas; os registros concretos ainda precisam ser inseridos.

Estrutura

Define quais dados podem existir.

Exemplo de estrutura
USUARIO(
    id_usuario PRIMARY KEY,
    nome NOT NULL
)

Ocorrência

É um caso concreto armazenado nessa estrutura.

Exemplo de ocorrência
id_usuario = 17
nome = 'Marina Lopes'
Não confunda tabela com registro

USUARIO é a estrutura que representa o tipo de informação. Marina Lopes é uma ocorrência que poderá ocupar uma linha dessa tabela. Essa distinção será importante para entender o que os comandos de DML realmente modificam.

Leia novamente o esquema

Que regras já estão esperando pelos dados?

Antes do primeiro INSERT, vale observar que as tabelas não estão vazias de significado. Mesmo sem registros, elas já possuem regras que vão decidir quais operações podem ou não ser aceitas.

USUARIO

id_usuario identifica uma ocorrência de forma única. O nome é obrigatório.

Pergunta: o que acontecerá se tentarmos usar o mesmo identificador duas vezes?

SALA

Cada sala possui identidade própria e referencia um bloco existente.

Pergunta: podemos cadastrar uma sala apontando para um bloco que ainda não existe?

RESERVA

Cada reserva referencia um usuário e uma sala e registra uma ocorrência em determinada data e horário.

Pergunta: podemos reservar uma sala para um usuário inexistente?

A virada desta aula

Da definição da estrutura para as operações sobre os dados

Até agora perguntávamos principalmente “como o banco deve ser organizado?”. A partir daqui a pergunta muda: “o que acontece quando tentamos inserir, consultar, alterar ou excluir uma ocorrência?”

INSERT

Cria novas ocorrências nas tabelas.

SELECT

Permite verificar quais ocorrências estão armazenadas e localizar aquelas que queremos manipular.

UPDATE e DELETE

Alteram ou removem ocorrências, sempre com atenção ao alcance da operação e às regras do banco.

O banco passa a responder às nossas tentativas

Quando uma operação for aceita, observaremos a mudança produzida. Quando for rejeitada, usaremos a mensagem de erro para identificar qual regra da estrutura foi violada.

O banco começa a ganhar ocorrências

Vamos cadastrar primeiro as ocorrências independentes e, logo depois de cada etapa, consultar o banco para verificar o que realmente foi armazenado.

Inserindo blocos

A ordem pode importar

Se uma sala referencia um bloco, esse bloco precisa existir antes que a sala seja inserida. A chave estrangeira transforma uma decisão de modelagem em uma regra observável durante a manipulação dos dados.

Teste proposital · bloco inexistente
INSERT INTO sala (id_sala, nome, capacidade, id_bloco)
VALUES (500, 'Sala Teste', 5, 99);
Antes de executar

O comando está sintaticamente correto. Mesmo assim, deve ser rejeitado porque a referência para o bloco 99 não corresponde a nenhuma ocorrência existente.

3 · Integridade e restrições

O banco não aceita qualquer valor apenas porque a sintaxe está correta

Agora vamos observar diferentes tipos de restrição e relacioná-los às regras do domínio.

RestriçãoPergunta que ela respondeExemplo no domínio
PRIMARY KEYComo identificar unicamente esta ocorrência?Duas ocorrências de USUARIO não podem compartilhar o mesmo id_usuario.
FOREIGN KEYA referência aponta para uma ocorrência existente?Uma RESERVA não pode apontar para um usuário inexistente.
NOT NULLEste dado pode ficar ausente?Uma sala precisa possuir nome.
CHECKEste valor satisfaz uma regra?A capacidade precisa ser maior que zero.
DEFAULTQue valor utilizar quando nenhum for informado?Uma nova reserva pode começar como ativa.
UNIQUEEste valor ou combinação pode aparecer novamente?A mesma sala não pode ser reservada duas vezes na mesma data e horário.

Integridade de entidade

Garante que cada ocorrência possa ser identificada. A chave primária é o mecanismo central desse controle.

Integridade referencial

Garante que uma referência existente em uma tabela aponte para uma ocorrência válida em outra tabela.

Integridade de domínio

Garante que os valores respeitem regras associadas aos atributos, como obrigatoriedade, faixa permitida ou conjunto de valores possíveis.

Mensagem de erro como evidência

Quando uma operação é rejeitada, o objetivo é descobrir qual regra foi violada e por que essa regra existe.

As regras já fazem parte do banco usado no exercício

Não vamos reconstruir as tabelas nesta aula. Vamos observar CHECK, DEFAULT, UNIQUE, PKs e FKs pelo comportamento das operações.

Teste · chave primária duplicada
INSERT INTO usuario (id_usuario, nome)
VALUES (17, 'Outra pessoa');
Teste · valor obrigatório ausente
INSERT INTO usuario (id_usuario, nome)
VALUES (90, NULL);
Teste · valor que viola CHECK
INSERT INTO reserva (
    id_reserva, id_usuario, id_sala, data, hora_inicio, situacao
)
VALUES (
    1, 17, 204, '2026-09-18', '18:30', 'aguardando'
);
DEFAULT em ação
INSERT INTO reserva (
    id_reserva, id_usuario, id_sala, data, hora_inicio
)
VALUES (
    2, 42, 204, '2026-09-19', '14:00'
);
Confira o valor assumido
SELECT *
FROM reserva
WHERE id_reserva = 2;
O valor não foi omitido do banco

Como a coluna possui DEFAULT 'ativa', a situação recebe esse valor quando ele não é informado no INSERT.

4 · UPDATE

Primeiro localize. Depois altere.

Antes de modificar uma ocorrência, use o mesmo filtro em um SELECT. Assim podemos confirmar exatamente qual linha será atingida.

1 · Localize
SELECT *
FROM reserva
WHERE id_reserva = 2;
2 · Altere
UPDATE reserva
SET situacao = 'cancelada'
WHERE id_reserva = 2;
3 · Confira
SELECT *
FROM reserva
WHERE id_reserva = 2;
Sem WHERE
UPDATE reserva
SET situacao = 'cancelada';
Não é um erro de SQL

Sem WHERE, todas as linhas da tabela podem ser alteradas. O comando pode estar correto sintaticamente e, ainda assim, produzir um resultado muito diferente do pretendido.

5 · DELETE e integridade referencial

Localize, exclua e verifique

O mesmo procedimento usado no UPDATE vale para exclusões: primeiro confirme a ocorrência, depois execute a operação e, por fim, verifique o resultado.

1 · Localize
SELECT *
FROM reserva
WHERE id_reserva = 2;
2 · Exclua
DELETE FROM reserva
WHERE id_reserva = 2;
3 · Verifique
SELECT *
FROM reserva
WHERE id_reserva = 2;
Exclusão sem filtro
DELETE FROM reserva;
Sem WHERE

O comando remove todas as linhas da tabela. Novamente, o problema não é sintático: é o alcance da operação.

ON DELETE

O que deve acontecer quando o registro referenciado desaparece?

A resposta depende da regra do domínio. A política deve ser decidida no relacionamento.

RESTRICT / NO ACTION

Impede a exclusão enquanto existirem registros dependentes.

CASCADE

Ao remover o registro referenciado, remove também os registros dependentes.

SET NULL

A referência passa a ser NULL, desde que a coluna aceite ausência de valor.

CASCADE não é uma opção automática

Apagar os telefones de um usuário removido pode ser coerente. Apagar todo o histórico de reservas desse usuário pode não ser. A escolha precisa representar o significado do relacionamento.

Prática em dupla · construa uma pequena história

Represente no banco a seguinte sequência:

  1. Cadastre Camila como usuária.
  2. Cadastre dois telefones para ela.
  3. Cadastre a Sala Pinheiro, capacidade 8, no Bloco B.
  4. Registre uma reserva da sala para 30/09/2026 às 19:00.
  5. Use SELECT para localizar a reserva.
  6. Cancele a reserva com UPDATE e confira a alteração.
  7. Escolha um registro que possa ser removido, localize-o primeiro e depois teste DELETE.

Ao final, provoque intencionalmente três erros: uma PK duplicada, uma FK para registro inexistente e uma situação inválida. Para cada um, explique qual regra foi violada.
