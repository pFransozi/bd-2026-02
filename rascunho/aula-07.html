Manipulação de dados e integridade

Na aula anterior o esquema virou tabelas, chaves e relacionamentos. Agora vamos colocar dados nessas estruturas e observar o que acontece quando uma operação respeita — ou viola — as regras que definimos.

Criar tabelas é suficiente para garantir que os dados armazenados estejam corretos?

Visão da aula

Do esquema vazio para dados consistentes

Objetivos de aprendizagem

  • Inserir registros com INSERT.
  • Alterar e excluir registros com UPDATE, DELETE e WHERE.
  • Interpretar violações de PK, FK e NOT NULL.
  • Compreender CHECK, DEFAULT e UNIQUE.
  • Analisar os efeitos de regras de exclusão referencial.

Ideia central

O foco não será decorar comandos. Em cada operação vamos perguntar: o banco deveria aceitar isso? Se não aceitar, qual regra do domínio está sendo preservada?

1 · Retomada

Onde terminamos na Aula 06?

O percurso já passou por requisitos, MER, DER, modelo relacional, normalização e criação das tabelas.

Domínio→MER / DER→Modelo relacional→Normalização→CREATE TABLE→Dados

USUARIO

id_usuario identifica cada usuário; nome é obrigatório.

SALA

id_sala identifica a sala; cada sala referencia um bloco.

RESERVA

id_reserva identifica a ocorrência e conecta um usuário a uma sala em data e horário determinados.

Estrutura e dados são coisas diferentes

CREATE TABLE define como os dados podem existir. Nesta aula, INSERT, UPDATE e DELETE vão manipular ocorrências concretas.

Preparação técnica da conexão
PRAGMA foreign_keys = ON;
Por que executar isso no início?

Para que as chaves estrangeiras sejam efetivamente verificadas durante os testes da aula. Assim, uma referência para um usuário, sala ou bloco inexistente será rejeitada.

2 · INSERT

O banco começa a ganhar ocorrências

Vamos cadastrar primeiro as ocorrências independentes e depois aquelas que dependem de referências já existentes.

Inserindo blocos
INSERT INTO bloco (id_bloco, nome_bloco)
VALUES
    (1, 'Bloco A'),
    (2, 'Bloco B'),
    (3, 'Bloco C');
Inserindo usuários
INSERT INTO usuario (id_usuario, nome)
VALUES
    (17, 'Marina Lopes'),
    (42, 'Gustavo Neri'),
    (8, 'Larissa Moura');
Inserindo salas
INSERT INTO sala (id_sala, nome, capacidade, id_bloco)
VALUES
    (204, 'Sala Ipê', 6, 2),
    (118, 'Sala Araucária', 8, 1),
    (305, 'Sala Horizonte', 4, 3);
A ordem importa

Uma sala referencia um bloco. Uma reserva referencia usuário e sala. Portanto, primeiro precisamos criar as ocorrências que serão referenciadas.

Teste propositalmente inválido
INSERT INTO sala (id_sala, nome, capacidade, id_bloco)
VALUES (500, 'Sala Teste', 4, 99);
Antes de executar

O bloco 99 existe? Se não existe, a inserção deve ser rejeitada pela integridade referencial.

3 · Integridade

As regras do modelo aparecem durante a manipulação

As restrições deixam de ser apenas conceitos do diagrama e passam a atuar sobre cada operação.

RestriçãoPergunta que respondeExemplo
PRIMARY KEYComo identificar unicamente esta ocorrência?Dois usuários não podem possuir o mesmo id_usuario.
FOREIGN KEYA referência aponta para algo que existe?Uma reserva não pode apontar para uma sala inexistente.
NOT NULLEste dado pode ficar ausente?Uma sala precisa ter nome e capacidade.
CHECKO valor satisfaz uma regra?A capacidade deve ser maior que zero.
DEFAULTQue valor usar quando nenhum for informado?Uma nova reserva pode começar como ativa.
UNIQUEEsta combinação pode se repetir?Evitar duas reservas para a mesma sala no mesmo horário.

Esquema usado nos testes

As regras adicionais entram na definição das tabelas

Para esta aula, o notebook pode preparar as tabelas já com as restrições que queremos observar.

Sala com regra de domínio
CREATE TABLE sala (
    id_sala INTEGER PRIMARY KEY,
    nome TEXT NOT NULL,
    capacidade INTEGER NOT NULL CHECK (capacidade > 0),
    id_bloco INTEGER NOT NULL,
    FOREIGN KEY (id_bloco) REFERENCES bloco(id_bloco)
);
Reserva com CHECK, DEFAULT e UNIQUE
CREATE TABLE reserva (
    id_reserva INTEGER PRIMARY KEY,
    id_usuario INTEGER NOT NULL,
    id_sala INTEGER NOT NULL,
    data TEXT NOT NULL,
    hora_inicio TEXT NOT NULL,
    situacao TEXT NOT NULL DEFAULT 'ativa'
        CHECK (situacao IN ('ativa', 'cancelada', 'concluida')),

    FOREIGN KEY (id_usuario) REFERENCES usuario(id_usuario),
    FOREIGN KEY (id_sala) REFERENCES sala(id_sala),
    UNIQUE (id_sala, data, hora_inicio)
);
Compatibilidade do exemplo

As novas regras são definidas diretamente no CREATE TABLE. Assim, não dependemos de comandos de alteração de estrutura que não são necessários para esta aula.

PK duplicada

INSERT INTO usuario (id_usuario, nome)
VALUES (17, 'Outra pessoa');

Deve falhar porque 17 já identifica Marina Lopes.

NOT NULL

INSERT INTO usuario (id_usuario, nome)
VALUES (90, NULL);

Deve falhar porque o nome foi definido como obrigatório.

CHECK

INSERT INTO sala (id_sala, nome, capacidade, id_bloco)
VALUES (700, 'Sala Azul', -5, 1);

A sintaxe está correta, mas o valor viola a regra capacidade > 0.

DEFAULT

INSERT INTO reserva (
    id_reserva, id_usuario, id_sala, data, hora_inicio
)
VALUES (1, 17, 204, '2026-09-20', '18:30');

Como situacao não foi informada, o valor padrão será ativa.

4 · UPDATE

Dados mudam — e o WHERE delimita o alcance

Cancelar uma reserva específica
UPDATE reserva
SET situacao = 'cancelada'
WHERE id_reserva = 1;
O perigo
UPDATE reserva
SET situacao = 'cancelada';
Isso não é um erro de SQL

Sem WHERE, todas as linhas da tabela são atualizadas. O comando pode estar sintaticamente perfeito e ainda assim produzir um resultado indesejado.

Rotina segura

Antes de um UPDATE, teste o mesmo filtro com SELECT. Se o filtro retorna exatamente as linhas desejadas, ele pode ser reaproveitado no comando de alteração.

Conferindo antes de alterar
SELECT *
FROM reserva
WHERE id_reserva = 1;

5 · DELETE

Excluir também exige critério

Exclusão específica
DELETE FROM reserva
WHERE id_reserva = 1;
Sem filtro
DELETE FROM reserva;
Qual é a consequência?

Sem WHERE, todas as reservas são removidas.

E quando outra tabela depende do registro?

Usuário ainda referenciado
DELETE FROM usuario
WHERE id_usuario = 17;

Se existirem reservas que apontam para esse usuário, a exclusão deve respeitar a política definida na chave estrangeira.

RESTRICT / NO ACTION

Impede a exclusão enquanto houver registros dependentes.

CASCADE

Exclui também os registros dependentes.

SET NULL

Substitui a referência por NULL, desde que a coluna permita valor nulo.

Exemplo de definição com CASCADE
CREATE TABLE telefone_usuario (
    id_usuario INTEGER NOT NULL,
    telefone TEXT NOT NULL,
    PRIMARY KEY (id_usuario, telefone),
    FOREIGN KEY (id_usuario)
        REFERENCES usuario(id_usuario)
        ON DELETE CASCADE
);
A política de exclusão é uma regra do domínio

Apagar os telefones junto com o usuário pode fazer sentido. Apagar todo o histórico de reservas do mesmo usuário talvez não faça. A escolha não deve ser automática.

Desafio em dupla · uma pequena história no banco

Represente a situação abaixo usando comandos SQL.

Camila foi cadastrada como usuária. Ela possui dois telefones. Uma nova sala chamada Sala Pinheiro, com capacidade para oito pessoas, foi cadastrada no Bloco B. Camila realizou uma reserva dessa sala para 30/09/2026 às 19h. Posteriormente, a reserva foi cancelada.

  1. Cadastre Camila.
  2. Cadastre seus dois telefones.
  3. Cadastre a sala.
  4. Registre a reserva.
  5. Altere a reserva para cancelada.
  6. Depois provoque, intencionalmente, uma violação de PK, uma de FK e uma de CHECK. Para cada uma, explique a mensagem recebida.

7 · Síntese

O banco agora tem estrutura, dados e regras atuando juntas

Requisitos→DER→Modelo relacional→DDL→Restrições→DML→Dados consistentes

O que desenvolvemos

Inserir, alterar e excluir não são operações isoladas. Cada comando é submetido às regras que representam identidade, domínio e relacionamentos.
