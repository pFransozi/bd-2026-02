1 · Conceitos fundamentais

O banco de dados não é o SGBD

Embora os termos sejam usados informalmente como sinônimos, eles designam elementos diferentes da arquitetura.

ElementoO que éExemplo no laboratório
Banco de dadosConjunto organizado de informações persistentes, estruturadas em tabelas e relacionamentos para representar um domínio e permitir sua recuperação.Banco que armazena salas, usuários, blocos e reservas.
SGBDSoftware que gerencia o armazenamento e o acesso aos bancos de dados, executa consultas e controla integridade, transações e permissões.Servidor PostgreSQL.
SQLLinguagem declarativa utilizada para criar estruturas, consultar e modificar dados; descreve a operação desejada, sem definir todos os passos de execução.SELECT, UPDATE, CREATE TABLE.

Por que o PostgreSQL é chamado objeto-relacional?

Seu fundamento continua sendo o modelo relacional, com tabelas, chaves, SQL e restrições. Além disso, ele oferece tipos de dados extensíveis, funções definidas pelo usuário, estruturas complexas e mecanismos de extensão. Um exemplo é o suporte a JSONB; outro é o uso de extensões como PostGIS para dados geoespaciais.

Portanto, “objeto-relacional” não significa que o PostgreSQL substitui a modelagem relacional por classes de uma linguagem de programação.

O que um SGBD acrescenta a um conjunto de arquivos?

Os arquivos armazenam os dados, mas o gerenciamento confiável exige mecanismos adicionais. No PostgreSQL, essas responsabilidades são concentradas no SGBD, que coordena como as informações são organizadas, consultadas, protegidas e recuperadas.

2 · Arquitetura e processamento

O que acontece entre executar um SELECT e receber o resultado?

Assim como o DBeaver, uma aplicação Python não consulta os arquivos do banco diretamente. Ela utiliza um driver para enviar SQL ao PostgreSQL, que interpreta, planeja e executa a instrução antes de devolver os resultados.

As etapas do processo

01 · Conexão

Python e psycopg

O código utiliza psycopg.connect() para abrir uma conexão. O driver implementa a comunicação entre a aplicação e o servidor.

02 · Envio

SQL parametrizada

O cursor envia a instrução com execute(sql, params). Parâmetros são passados separadamente do texto SQL.

03 · Análise

Interpretação e validação

O PostgreSQL verifica sintaxe, referências a objetos, tipos e permissões necessárias.

04 · Planejamento

Estratégia de execução

O otimizador compara planos e estima custos, podendo escolher varredura sequencial, índices e diferentes algoritmos de junção.

05 · Execução

Acesso aos dados

O executor acessa buffers, páginas e índices, considera a visibilidade das versões e produz os registros solicitados.

06 · Retorno

Linhas no Python

O resultado volta ao programa, que pode recuperar uma linha com fetchone() ou todas as linhas restantes com fetchall().

Exemplo de uma consulta SQL executada pelo Python

Para conversar com o PostgreSQL, utilizaremos a biblioteca psycopg 3. O código abaixo consulta as salas com capacidade mínima de oito pessoas e identifica o bloco ao qual cada sala pertence.

Instalação do driverTerminal
python -m pip install "psycopg[binary]"
Python · conexão, SELECT e retorno de linhaspsycopg 3
import os
import psycopg

with psycopg.connect(
    host=os.getenv("PGHOST", "localhost"),
    port=int(os.getenv("PGPORT", "5432")),
    dbname=os.getenv("PGDATABASE", "postgres"),
    user=os.getenv("PGUSER", "postgres"),
    password=os.getenv("PGPASSWORD"),
) as conn:
    with conn.cursor() as cur:
        cur.execute(
            """
            SELECT s.nome AS sala,
                   b.nome_bloco AS bloco,
                   s.capacidade
            FROM sala AS s
            JOIN bloco AS b ON b.id_bloco = s.id_bloco
            WHERE s.capacidade >= %s
            ORDER BY s.nome
            """,
            (8,)
        )

        for sala, bloco, capacidade in cur.fetchall():
            print(f"{sala} ({bloco}): {capacidade} lugares")

A conexão usa as variáveis de ambiente PGHOST, PGPORT, PGDATABASE, PGUSER e PGPASSWORD. Ajuste esses valores ao seu ambiente, sem colocar senhas diretamente no código. As tabelas sala e bloco são criadas no laboratório indicado adiante.

Por que %s e (8,)? O marcador %s representa um parâmetro SQL e (8,) é uma tupla Python com o valor mínimo de capacidade enviado. Assim, os valores são separados do comando e não são concatenados à SQL, ajudando a prevenir injeção de SQL.

Principais funções e métodos do psycopg

O driver oferece objetos de conexão e cursores. Os métodos abaixo são suficientes para iniciar a integração entre Python e PostgreSQL:

Função ou métodoO que fazQuando utilizar
psycopg.connect()Estabelece a conexão com o servidor PostgreSQL.Início do acesso ao banco de dados.
conn.cursor()Cria um cursor para enviar comandos e ler resultados.Antes de executar operações SQL.

No exemplo, os blocos with encerram os recursos. A conexão confirma uma transação bem-sucedida ou realiza rollback diante de uma exceção. Em consultas simples, não é necessário chamar commit() manualmente.

Como os dados são armazenados?

A aplicação vê tabelas, colunas e registros. Internamente, o PostgreSQL organiza informações em arquivos e páginas de dados, utiliza memória compartilhada para armazenar páginas em buffer e mantém estruturas auxiliares, como índices e registros de WAL.

Visão lógica

Banco → esquema → tabela → linha/coluna. É a visão utilizada para modelar e consultar os dados.

Visão física

Páginas → arquivos → índices e buffers. É a organização que o SGBD administra para realizar as operações.

Essa separação é uma forma de independência de dados: aplicações normalmente não precisam conhecer a posição física de cada registro.

Pergunta de análise

Se duas consultas devolvem o mesmo conjunto de registros, elas precisam executar exatamente o mesmo percurso físico?

Não. O PostgreSQL estima o custo das alternativas usando estatísticas das tabelas (atualizadas pelo ANALYZE), índices disponíveis e estratégias como varredura sequencial ou por índice, diferentes algoritmos de JOIN e, quando adequado, execução paralela. O comando EXPLAIN mostra o plano escolhido.

4.1 · Integridade: impedir estados inválidos

Ao definir CHECK (capacidade > 0) na tabela sala, impedimos capacidades inválidas. Uma chave estrangeira na tabela reserva impede que uma reserva seja associada a um usuário ou a uma sala inexistente.

Outras regras exigem uma modelagem apropriada. Por exemplo, UNIQUE (id_sala, data, hora_inicio) impede que a mesma sala seja reservada duas vezes no mesmo horário, enquanto transações coordenam alterações que precisam ocorrer em conjunto.

4.2 · Transações: uma unidade lógica de trabalho

Uma transação pode reunir operações relacionadas. Se todas forem válidas, confirmamos; se ocorrer um erro e decidirmos cancelar, desfazemos a unidade de trabalho.

COMMIT

Confirma as alterações da transação, tornando-as permanentes segundo as garantias configuradas.

ROLLBACK

Desfaz as alterações não confirmadas da transação.

As quatro propriedades ACID

PropriedadeSignificado didáticoNo sistema de reservas
AtomicidadeAs alterações da transação são confirmadas ou desfeitas como uma unidade.Não confirmar alterações parciais de uma reserva.
ConsistênciaPreservar os invariantes e restrições efetivamente declarados.Uma reserva deve referenciar uma sala existente e respeitar as restrições do esquema.
IsolamentoControlar como transações concorrentes observam ou interferem nos dados.Duas tentativas simultâneas de reservar o mesmo horário precisam ser coordenadas.
DurabilidadeManter alterações confirmadas apesar de falhas, dentro das garantias configuradas.Uma reserva confirmada deve permanecer registrada após uma falha.

4.3 · Índices e processamento de consultas

Um índice é uma estrutura auxiliar utilizada para localizar registros com menos trabalho em determinadas consultas. Ele pode acelerar filtros seletivos, mas ocupa espaço e precisa ser mantido quando os dados mudam.

Observar o plano antes de otimizarSQL
EXPLAIN
SELECT id_sala, nome, capacidade
FROM sala
WHERE id_sala = 118;

Um plano com Seq Scan percorre a tabela; um plano com Index Scan ou Bitmap Index Scan usa um índice. Em uma tabela muito pequena, a varredura sequencial pode ser a melhor escolha, mesmo com índice disponível.

Importante: o custo mostrado pelo EXPLAIN é uma estimativa em unidades internas, não uma medida direta de milissegundos. Já EXPLAIN ANALYZE executa a consulta e informa tempos observados.

4.4 · Segurança: autenticação e autorização

Autenticação responde “quem está tentando acessar?”. Autorização responde “o que essa identidade pode fazer?”. O PostgreSQL oferece papéis, políticas de acesso e privilégios sobre bancos, esquemas, tabelas e outros objetos.

Exemplo conceitual · requer papel criado e privilégios adequadosSQL
GRANT SELECT ON sala, reserva TO papel_consulta;
REVOKE INSERT, UPDATE, DELETE
ON sala, reserva FROM papel_consulta;
Os comandos ilustram autorização. Não execute sem antes criar o papel e conhecer as permissões do ambiente.

O SGBD pode restringir operações, mas a segurança do sistema também depende da aplicação, da rede, das credenciais e das práticas de desenvolvimento.

4.5 · Recuperação: falha de servidor não é o mesmo que exclusão indevida

O PostgreSQL utiliza WAL (Write-Ahead Logging) para registrar modificações antes de sua efetivação nos arquivos de dados. Após determinadas falhas, esses registros permitem refazer alterações necessárias à recuperação.

WAL

Fundamenta a recuperação de alterações após interrupções e pode apoiar recuperação por ponto no tempo quando há arquivamento configurado.

Backup

Cópia para restauração: por exemplo, exportação lógica com pg_dump e restauração com pg_restore.

Replicação

Manutenção de cópias em outras instâncias para disponibilidade ou distribuição de leituras. Não substitui necessariamente backups.

Discussão

Se um operador excluir registros por engano e essa exclusão for replicada, ter uma réplica basta para recuperar os registros?

Não necessariamente. Uma estratégia de restauração precisa considerar backups e, quando pertinente, recuperação por ponto no tempo.

4.6 · Recursos para além da SQL básica

Views permitem reutilizar consultas; materialized views armazenam resultados que precisam ser atualizados; functions e procedures organizam rotinas; triggers reagem a eventos. O PostgreSQL também suporta tipos como JSONB e extensões especializadas.

O objetivo não é colocar toda a lógica de negócio dentro do banco. A decisão depende de requisitos de integridade, manutenção, desempenho e divisão de responsabilidades da aplicação.

4 · Concorrência

Por que várias pessoas podem consultar e atualizar ao mesmo tempo?

Em um sistema web, requisições chegam simultaneamente. O PostgreSQL precisa coordenar esse trabalho sem tornar todas as operações uma única fila.

MVCC: múltiplas versões dos dados

O MVCC (Multiversion Concurrency Control) permite que leituras trabalhem com visões consistentes de versões dos registros. Em muitas situações, leituras comuns não bloqueiam operações de escrita, e escritas não bloqueiam essas leituras.

Isso não significa ausência de bloqueios. Duas transações que tentam registrar reservas incompatíveis podem precisar esperar uma pela outra. A visibilidade de cada alteração também depende do nível de isolamento.

Transação AReserva a Sala Jacarandá às 14h
↔
PostgreSQLVersões + bloqueios + restrições
↔
Transação BTenta reservar a mesma sala e horário

O gerenciamento de concorrência combina visibilidade de versões, coordenação de conflitos e verificação das restrições.

O erro de separar verificação e reserva

Estratégia frágil · verificação seguida de uma operação independenteExemplo
SELECT COUNT(*) AS reservas_existentes
FROM reserva
WHERE id_sala = 403
  AND data = DATE '2026-11-12'
  AND hora_inicio = TIME '14:00';

-- A aplicação decide, depois, se fará INSERT.

Se duas aplicações consultarem o horário ao mesmo tempo, ambas poderão encontrar zero reservas. Essa leitura, isoladamente, não garante exclusividade: outra transação pode registrar uma reserva antes da inserção.

Uma inserção protegida pela restrição de unicidade

Reserva de sala · conflito verificado pelo SGBDSQL
INSERT INTO reserva
    (id_reserva, id_usuario, id_sala, data, hora_inicio)
VALUES
    (30, 17, 403, DATE '2026-11-12', TIME '14:00')
ON CONFLICT (id_sala, data, hora_inicio) DO NOTHING
RETURNING id_reserva;

A restrição UNIQUE (id_sala, data, hora_inicio) impede a duplicidade mesmo sob acessos simultâneos. Com ON CONFLICT DO NOTHING, a operação não insere a linha conflitante; se não houver reserva possível, RETURNING não devolve registros.

A verificação de disponibilidade não substitui a restrição do banco. Neste modelo, a unicidade vale para qualquer situação da reserva, inclusive cancelada; permitir reutilização de horários cancelados exigiria uma regra de integridade diferente.

UPDATE reserva
SET situacao = 'cancelada'
WHERE id_reserva = 1;

SELECT id_reserva, situacao
FROM reserva
WHERE id_reserva = 1;

ROLLBACK;

SELECT id_reserva, situacao
FROM reserva
WHERE id_reserva = 1;

Antes do ROLLBACK, a própria conexão observa cancelada. Depois, a situação volta a ser ativa. Substituir o ROLLBACK por COMMIT confirmaria a alteração.

Qual a diferença entre desfazer e confirmar?

O ROLLBACK cancela as alterações não confirmadas da transação. O COMMIT confirma a transação. Uma alteração já confirmada não é desfeita simplesmente executando um ROLLBACK posterior.

Experimento 3 · Duas conexões disputando o mesmo horário

Abra duas conexões distintas ao mesmo banco (sessões A e B) no DBeaver ou dois terminais psql. Os comandos devem permanecer na mesma conexão durante cada transação. No DBeaver, confira a configuração de autocommit e mantenha a transação aberta até sua confirmação ou cancelamento.

Sessão A · Primeira reserva

Registra a Sala Jacarandá para um horário ainda disponível, mas não confirma a transação.

Executar primeiro
BEGIN;

INSERT INTO reserva
    (id_reserva, id_usuario, id_sala,
     data, hora_inicio, observacao)
VALUES
    (21, 17, 403, DATE '2026-11-12',
     TIME '14:00', 'Reunião de projeto');

-- Não executar COMMIT ainda.

Sessão B · Reserva concorrente

Com A ainda aberta, outra pessoa tenta reservar a mesma sala, data e horário.

Executar depois de A
BEGIN;

INSERT INTO reserva
    (id_reserva, id_usuario, id_sala,
     data, hora_inicio, observacao)
VALUES
    (22, 42, 403, DATE '2026-11-12',
     TIME '14:00', 'Reunião de equipe');

-- Aguardar a conclusão da sessão A.
  1. Na sessão A, execute COMMIT;.
  2. Observe a sessão B: ao prosseguir, o PostgreSQL rejeita a inserção conflitante pela restrição UNIQUE (id_sala, data, hora_inicio).
  3. Na sessão B, execute ROLLBACK; para encerrar a transação que apresentou erro.
  4. Confirme o resultado final com a consulta abaixo em qualquer conexão.
Passo final · ConferênciaSQL
SELECT r.id_reserva,
       u.nome AS usuario,
       s.nome AS sala,
       r.data,
       r.hora_inicio
FROM reserva AS r
JOIN usuario AS u ON u.id_usuario = r.id_usuario
JOIN sala AS s ON s.id_sala = r.id_sala
WHERE r.id_sala = 403
  AND r.data = DATE '2026-11-12'
  AND r.hora_inicio = TIME '14:00';
Resultado esperado e interpretação

O resultado deve mostrar uma única reserva, de Marina Lopes para a Sala Jacarandá, em 12/11/2026 às 14h. A tentativa concorrente foi rejeitada porque as duas linhas teriam a mesma combinação de sala, data e horário. O experimento pressupõe a carga inicial deste laboratório.

Experimento 4 · Por que um índice pode modificar o plano?

Uma tabela com poucas reservas não permite observar claramente o impacto de índices. Por isso, vamos criar uma tabela auxiliar de teste com 100 mil registros sintéticos, simulando consultas por sala e data.

Comparação de planos em dados artificiaisSQL
DROP TABLE IF EXISTS reservas_desempenho;

CREATE TABLE reservas_desempenho (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    id_sala INTEGER NOT NULL,
    data DATE NOT NULL
);

INSERT INTO reservas_desempenho (id_sala, data)
SELECT
    CASE g % 4
        WHEN 0 THEN 118
        WHEN 1 THEN 204
        WHEN 2 THEN 305
        ELSE 403
    END,
    DATE '2026-01-01' + (g % 365)
FROM generate_series(1, 100000) AS g;

ANALYZE reservas_desempenho;

EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM reservas_desempenho
WHERE id_sala = 204
  AND data = DATE '2026-10-08';

CREATE INDEX idx_reservas_desempenho_sala_data
ON reservas_desempenho (id_sala, data);

ANALYZE reservas_desempenho;

EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM reservas_desempenho
WHERE id_sala = 204
  AND data = DATE '2026-10-08';

Compare o tipo de varredura, o número estimado e efetivo de linhas, o tempo observado e a utilização dos buffers. Não compare apenas o tempo de duas execuções isoladas: cache, ambiente e planejamento podem variar.

Questão de interpretação

Por que um índice pode acelerar uma consulta e, ao mesmo tempo, aumentar o custo de inserções ou atualizações?

O índice é uma estrutura adicional que precisa ser mantida, mas pode reduzir o trabalho de localização em determinadas consultas.

6 · Usos e decisões de projeto

Quando um SGBD é uma boa escolha?

Não basta perguntar se há muitos dados. É necessário avaliar requisitos de integridade, concorrência, consultas, segurança e continuidade do serviço.

ContextoO que precisa ser administradoMecanismos especialmente importantes
Comércio eletrônicoPedidos, estoque e registros de pagamento.Transações, concorrência e integridade.
HospitalPacientes, atendimentos e acesso por perfis.Controle de acesso, integridade e auditoria.
Instituição de ensinoMatrículas, turmas, notas e históricos.Relacionamentos, restrições e consultas.
IndústriaEquipamentos, ordens e histórico de manutenção.Persistência, disponibilidade e relatórios.
Aplicação webUsuários, conteúdo e operações simultâneas.Conexões, consultas, transações e permissões.

Quando um arquivo simples pode ser suficiente?

Um CSV local pode atender a uma análise pontual, e um JSON pode servir como arquivo de configuração. Se os dados forem poucos, estáticos, sem acessos simultâneos e sem requisitos transacionais, um SGBD servidor pode introduzir complexidade desnecessária.

Critério de engenharia: selecionar uma solução pela necessidade do sistema — não apenas pela popularidade da ferramenta.

Atividade de consolidação · Sistema de reserva de salas

Uma aplicação permite consultar salas, verificar horários, registrar e cancelar reservas. Usuários distintos podem acessar o sistema simultaneamente, e somente pessoas autorizadas devem modificar os registros.

Para cada situação, identifique o mecanismo do SGBD mais relevante e explique o que ainda precisará ser definido pelo projetista.

1. Uma reserva não pode referenciar uma sala inexistente.

Integridade referencial: chave estrangeira de reserva.id_sala para sala.id_sala.

2. Dois usuários tentam reservar a mesma sala para a mesma data e horário.

Concorrência e integridade: a restrição UNIQUE (id_sala, data, hora_inicio) impede a duplicidade. A aplicação precisa tratar adequadamente o conflito.

3. Uma pessoa pode consultar salas, mas não alterar reservas.

Autorização: papéis e privilégios podem conceder acesso de leitura sem permitir inserção, atualização ou exclusão.

4. O servidor desliga inesperadamente depois da confirmação de uma reserva.

Durabilidade e recuperação: o WAL e as configurações de persistência sustentam a recuperação de transações confirmadas.

5. A consulta de reservas por sala e data está lenta.

Planejamento e otimização: analisar o EXPLAIN, as estatísticas e índices adequados à combinação de sala e data.

6. Reservas são excluídas indevidamente e a exclusão chega às réplicas.

Backups e, se configurada, recuperação por ponto no tempo. Replicação não substitui uma estratégia de restauração.

7 · Síntese

O papel do SGBD na arquitetura do software

O PostgreSQL não é apenas um programa capaz de executar SELECT. Ele coordena a interpretação dos comandos, o armazenamento físico, as operações concorrentes e os mecanismos que tornam os dados utilizáveis de forma confiável.

O SGBD faz

Executa consultas, verifica restrições declaradas, controla transações, gerencia concorrência, administra permissões e oferece recuperação.

O projeto precisa definir

Regras do domínio, esquema e índices, transações corretas, políticas de acesso, estratégias de backup e requisitos de operação.
