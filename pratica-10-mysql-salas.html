Preparação para a prática

Este material é um roteiro de execução. Você utilizará primeiro o Workbench para criar e consultar tabelas, observará mecanismos do MySQL e, ao final, executará uma aplicação Python conectada ao mesmo banco.

Parte 1 · Workbench

Conferir a conexão, criar um esquema para a prática, construir quatro tabelas e cadastrar registros iniciais.

Parte 2 · Recursos do SGBD

Consultas, restrições, transações, índices e dois acessos simultâneos.

Parte 3 · Python

Preparar os arquivos, conectar com o Connector/Python, consultar registros e testar novas reservas.

Tempo de referência

Três blocos de aproximadamente 30, 50 e 50 minutos. Prossiga somente após conferir o resultado de cada etapa.

Ambiente para a prática

Os guias usam o MySQL Server 8.4 LTS. Se o servidor já estiver instalado, use a versão 8.0.16 ou posterior para que o MySQL verifique as restrições CHECK. Abra o MySQL Workbench. Para uma instalação local, use 127.0.0.1 e a porta configurada no seu ambiente. O guia nativo usa 3306 por padrão e o guia com Docker Desktop publica 3307.

Os guias mostram como testar a conexão e preparar a conta de aluno e o banco pratica_salas. Guia de instalação nativa · Guia com Docker Desktop.

Banco da prática

Use um esquema vazio chamado pratica_salas ou o esquema vazio atribuído para a atividade. Se usar outro nome, ajuste os comandos USE e o arquivo .env.

Como acompanhar: em cada etapa, identifique o programa indicado (PowerShell, Workbench ou Python), execute os comandos na ordem apresentada e leia a caixa “Confira antes de avançar”. Em algumas etapas, uma mensagem de erro será o resultado esperado.

1 · Primeiro contato com o Workbench

Parte 1 · Conhecer o ambiente e preparar o banco 30 minutos

01

Conferir a conexão com o MySQL

Onde executar · MySQL Workbench.

  1. Na tela inicial do Workbench, abra a conexão do laboratório. Para cadastrar uma conexão, clique em + ao lado de MySQL Connections. Preencha Connection Name e escolha Standard (TCP/IP) em Connection Method.
  2. Informe Hostname, Port, Username e a senha da conta. Em Default Schema, use o banco já preparado para sua conta, como laboratorio. Você selecionará pratica_salas na próxima etapa.
  3. Na aba SSL, selecione Require no campo Use SSL. Clique em Test Connection e, depois da confirmação, clique em OK e abra a conexão salva.
  4. No editor SQL, cole e selecione o bloco abaixo. Use Ctrl + Shift + Enter para executar a seleção. Para executar apenas a instrução em que está o cursor, use Ctrl + Enter.
SQL · conferir a sessão
SELECT VERSION() AS versao,
       CURRENT_USER() AS conta,
       @@port AS porta_servidor,
       @@SESSION.autocommit AS autocommit;

Confira antes de avançar

Confira a versão, a conta autenticada e a porta do servidor. Para configurar o Python, anote o host e a porta que você informou no cliente. A coluna autocommit vale 1 quando instruções individuais são confirmadas automaticamente fora de uma transação explícita.

02

Criar e selecionar o esquema da prática

Onde executar · editor SQL do Workbench, na conexão aberta para a prática.

No MySQL, database e schema são nomes para a mesma estrutura. Execute o bloco para criar e selecionar pratica_salas. O conjunto de caracteres utf8mb4 permite armazenar nomes com acentos.

SQL · preparar e selecionar o esquema
SET SESSION autocommit = 1;
CREATE DATABASE IF NOT EXISTS pratica_salas CHARACTER SET utf8mb4;
USE pratica_salas;
SELECT DATABASE() AS banco;
SHOW TABLES;

Se o esquema já foi preparado e a conta de aluno tem acesso a ele, você pode selecionar e executar o bloco a partir de USE. Use o nome do esquema que foi atribuído à sua conta. Atualize o painel Schemas para visualizá-lo.

Confira antes de avançar

O Result Grid deve mostrar o esquema escolhido em banco. Em um esquema vazio, SHOW TABLES devolve zero linhas. Se as quatro tabelas da prática já existirem, confira a carga na etapa 03 antes de inserir registros.

03

Criar as tabelas e inserir os primeiros registros

Onde executar: editor SQL do banco pratica_salas. Você criará as tabelas bloco, sala, usuario e reserva, nesta ordem.

bloco1 → Nsala1 → NreservaN ← 1usuario

1. Abra uma nova consulta e crie a tabela bloco. Observe que AUTO_INCREMENT gera id_bloco e que ENGINE=InnoDB define o mecanismo da tabela.

Workbench · SQL · tabela bloco
CREATE TABLE bloco (
    id_bloco INT AUTO_INCREMENT PRIMARY KEY,
    nome_bloco VARCHAR(60) NOT NULL UNIQUE
) ENGINE=InnoDB;

2. Crie a tabela sala. A declaração FOREIGN KEY faz id_bloco referenciar a tabela anterior. A restrição CHECK permite capacidades entre 1 e 80.

Workbench · SQL · tabela sala
CREATE TABLE sala (
    id_sala INT AUTO_INCREMENT PRIMARY KEY,
    id_bloco INT NOT NULL,
    nome VARCHAR(60) NOT NULL,
    capacidade INT NOT NULL,
    ativa BOOLEAN NOT NULL DEFAULT TRUE,
    CONSTRAINT fk_sala_bloco FOREIGN KEY (id_bloco) REFERENCES bloco (id_bloco),
    CONSTRAINT ck_sala_capacidade CHECK (capacidade BETWEEN 1 AND 80),
    CONSTRAINT uq_sala_bloco UNIQUE (id_bloco, nome)
) ENGINE=InnoDB;

3. Crie usuario. O UNIQUE evita dois registros com o mesmo e-mail.

Workbench · SQL · tabela usuario
CREATE TABLE usuario (
    id_usuario INT AUTO_INCREMENT PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    email VARCHAR(120) NOT NULL UNIQUE
) ENGINE=InnoDB;

4. Crie reserva. Cada registro apontará para uma sala e um usuário. O sistema considerará horários de uma hora, começando em hora cheia entre 08:00 e 21:00.

Workbench · SQL · tabela reserva
CREATE TABLE reserva (
    id_reserva INT AUTO_INCREMENT PRIMARY KEY,
    id_sala INT NOT NULL,
    id_usuario INT NOT NULL,
    data_reserva DATE NOT NULL,
    hora_inicio TIME NOT NULL,
    finalidade VARCHAR(160) NOT NULL,
    criado_em TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_reserva_sala FOREIGN KEY (id_sala) REFERENCES sala (id_sala),
    CONSTRAINT fk_reserva_usuario FOREIGN KEY (id_usuario) REFERENCES usuario (id_usuario),
    CONSTRAINT ck_reserva_hora CHECK (
        hora_inicio >= TIME '08:00:00'
        AND hora_inicio < TIME '22:00:00'
        AND MINUTE(hora_inicio) = 0
        AND SECOND(hora_inicio) = 0
    ),
    CONSTRAINT uq_sala_horario UNIQUE (id_sala, data_reserva, hora_inicio)
) ENGINE=InnoDB;

5. No painel Schemas do Workbench, atualize a lista e expanda pratica_salas → Tables. Confira se as quatro tabelas aparecem. Depois insira dois blocos e quatro salas:

Workbench · SQL · inserir blocos e salas
INSERT INTO bloco (nome_bloco)
VALUES ('Bloco A'), ('Bloco B');

INSERT INTO sala (id_bloco, nome, capacidade, ativa)
VALUES
    (1, 'Laboratório 101', 36, TRUE),
    (1, 'Sala 102', 45, TRUE),
    (2, 'Sala 201', 30, TRUE),
    (2, 'Laboratório 202', 24, TRUE);

6. Insira três usuários e quatro reservas iniciais:

Workbench · SQL · inserir usuários e reservas
INSERT INTO usuario (nome, email)
VALUES
    ('Ana Martins', 'ana.martins@exemplo.edu'),
    ('Bruno Costa', 'bruno.costa@exemplo.edu'),
    ('Carla Souza', 'carla.souza@exemplo.edu');

INSERT INTO reserva (id_sala, id_usuario, data_reserva, hora_inicio, finalidade)
VALUES
    (1, 1, '2026-11-12', '08:00:00', 'Aula de Banco de Dados'),
    (2, 2, '2026-11-12', '08:00:00', 'Projeto de Software'),
    (1, 3, '2026-11-12', '10:00:00', 'Monitoria'),
    (3, 2, '2026-11-13', '14:00:00', 'Reunião de projeto');

7. Conte os registros cadastrados:

Workbench · SQL · conferir a carga
SELECT
    (SELECT COUNT(*) FROM bloco) AS blocos,
    (SELECT COUNT(*) FROM sala) AS salas,
    (SELECT COUNT(*) FROM usuario) AS usuarios,
    (SELECT COUNT(*) FROM reserva) AS reservas;

Confira antes de avançar

O resultado deve ser 2 blocos, 4 salas, 3 usuários e 4 reservas. Se aparecer Table already exists ou um e-mail duplicado, use a contagem para identificar quais tabelas e registros já existem antes de retomar a etapa.

Arquivo de apoio: baixar o SQL completo. O arquivo reúne a criação, a carga e a conferência em um só lugar. Escolha a execução por etapas ou pelo arquivo para carregar os dados uma vez.

2 · Como o SGBD garante consistência

Parte 2 · Observar o trabalho do SGBD 50 minutos

04

Consultar salas, reservas e estrutura das tabelas

Onde executar: editor SQL do banco pratica_salas.

1. Execute uma consulta que relacione cada sala ao seu bloco:

SQL · listar salas e blocos
SELECT s.id_sala, s.nome AS sala,
       b.nome_bloco AS bloco, s.capacidade
FROM sala AS s
JOIN bloco AS b ON b.id_bloco = s.id_bloco
ORDER BY s.id_sala;

Na aba Result Grid, identifique a coluna bloco. Ela foi obtida da tabela bloco por meio do JOIN. O resultado deve ter 4 linhas.

2. Agora inclua WHERE antes de ORDER BY e consulte apenas salas com capacidade de pelo menos 30 lugares:

SQL · filtrar capacidade
SELECT s.nome AS sala, s.capacidade
FROM sala AS s
WHERE s.capacidade >= 30
ORDER BY s.nome;

O resultado deve mostrar 3 salas. O Laboratório 202 não aparece porque tem capacidade 24.

3. Execute uma consulta que combina três tabelas para mostrar as reservas iniciais:

SQL · reservas com nomes
SELECT r.data_reserva, r.hora_inicio,
       s.nome AS sala, u.nome AS solicitante, r.finalidade
FROM reserva AS r
JOIN sala AS s ON s.id_sala = r.id_sala
JOIN usuario AS u ON u.id_usuario = r.id_usuario
ORDER BY r.data_reserva, r.hora_inicio, s.nome;

Confira as 4 reservas. Os nomes das salas e dos usuários não estão gravados na tabela reserva; foram recuperados pelas chaves estrangeiras.

4. Por último, veja como o MySQL descreve a própria tabela reserva:

SQL · metadados
SELECT column_name, data_type
FROM information_schema.columns
WHERE table_schema = DATABASE()
  AND table_name = 'reserva'
ORDER BY ordinal_position;

Confira antes de avançar

A consulta de metadados deve listar as colunas da tabela reserva, como id_reserva, id_sala, id_usuario e hora_inicio. O information_schema descreve as estruturas. Experimente também SHOW CREATE TABLE reserva; para ver as restrições e o mecanismo InnoDB.

05

Observar como o MySQL rejeita dados inválidos

Onde executar: editor SQL. Cada tentativa abaixo é intencionalmente inválida. Execute os comandos separadamente e leia a mensagem no painel Action Output.

Uma mensagem de erro é esperada. Compare o código do erro com a restrição que a instrução testa. Faça os três testes separadamente, fora da transação da etapa seguinte.

1. Teste de capacidade: tente cadastrar uma sala com capacidade negativa.

SQL · teste A · CHECK
INSERT INTO sala (id_bloco, nome, capacidade)
VALUES (1, 'Sala impossível', -5);

O erro esperado é 3819 e aponta para ck_sala_capacidade. A tabela sala possui a condição capacidade BETWEEN 1 AND 80.

2. Teste de chave estrangeira: tente cadastrar uma reserva associada ao usuário 999, que não existe.

SQL · teste B · FOREIGN KEY
INSERT INTO reserva (id_sala, id_usuario, data_reserva, hora_inicio, finalidade)
VALUES (1, 999, '2026-11-12', '12:00:00', 'Teste de referência');

O erro esperado é 1452 e aponta para a chave estrangeira fk_reserva_usuario.

3. Teste de duplicidade: tente reservar a sala 1 no mesmo dia e horário de uma reserva já cadastrada.

SQL · teste C · UNIQUE
INSERT INTO reserva (id_sala, id_usuario, data_reserva, hora_inicio, finalidade)
VALUES (1, 2, '2026-11-12', '08:00:00', 'Reserva conflitante');

O erro esperado é 1062 (Duplicate entry) e aponta para o índice único uq_sala_horario.

4. Execute a consulta para conferir que nenhum dos testes inválidos criou registros:

SQL · conferir total
SELECT COUNT(*) AS total_reservas FROM reserva;

Confira antes de avançar

O total ainda deve ser 4 reservas. Os erros correspondem, na ordem, a CHECK, FOREIGN KEY e UNIQUE. O InnoDB e o servidor MySQL verificam essas regras quando o cliente envia cada INSERT.

06

Desfazer e confirmar uma alteração

Onde executar: editor SQL, na mesma aba durante toda a etapa. Execute um bloco por vez e confira o valor apresentado em cada consulta. A transação explícita agrupa as operações mesmo com autocommit ativo.

1. Consulte a capacidade atual da sala 1:

SQL · valor inicial
SELECT id_sala, nome, capacidade
FROM sala WHERE id_sala = 1;

O valor inicial deve ser 36.

2. Inicie uma transação:

SQL · iniciar transação
START TRANSACTION;

3. Altere temporariamente a capacidade para 50 e consulte novamente:

SQL · alterar e observar
UPDATE sala SET capacidade = 50 WHERE id_sala = 1;

SELECT capacidade FROM sala WHERE id_sala = 1;

O resultado na mesma sessão deve ser 50. Essa mudança ainda não foi confirmada.

4. Desfaça a alteração e consulte mais uma vez:

SQL · desfazer
ROLLBACK;

SELECT capacidade FROM sala WHERE id_sala = 1;

O valor deve voltar para 36.

5. Inicie uma nova transação, atualize a capacidade para 40 e confirme:

SQL · confirmar
START TRANSACTION;
UPDATE sala SET capacidade = 40 WHERE id_sala = 1;
COMMIT;

SELECT capacidade FROM sala WHERE id_sala = 1;

Confira antes de avançar

A sequência é 36 → 50 → 36 → 40. Depois do ROLLBACK, o valor volta a 36. Depois do COMMIT, o valor confirmado é 40.

07

Visualizar índices, plano de execução e permissões

Onde executar: editor SQL do banco pratica_salas.

1. Descubra quais índices o MySQL mantém para a tabela reserva:

SQL · consultar índices
SHOW INDEX FROM reserva;

Na coluna Key_name, localize PRIMARY e uq_sala_horario. Cada linha de uq_sala_horario descreve uma coluna do índice. Use Seq_in_index para conferir a ordem.

2. Peça ao MySQL para mostrar o plano que escolheria para localizar uma reserva específica:

SQL · observar plano
EXPLAIN FORMAT=TRADITIONAL
SELECT id_reserva, id_usuario
FROM reserva
WHERE id_sala = 1
  AND data_reserva = '2026-11-12'
  AND hora_inicio = '08:00:00';

Leia type, key e rows. A busca usa todos os campos de uma chave única, por isso o resultado esperado é type = const e key = uq_sala_horario.

3. Verifique o usuário conectado e seus privilégios básicos na tabela:

SQL · consultar permissões
SELECT CURRENT_USER() AS conta;
SHOW GRANTS FOR CURRENT_USER();

Confira antes de avançar

Identifique o índice escolhido e a estimativa de linhas em rows. Nas concessões, procure SELECT, INSERT ou ALL PRIVILEGES e confira a quais bancos ou tabelas se aplicam. Se a conta usa papéis, SELECT CURRENT_ROLE(); mostra os papéis ativos.

08

Usar duas conexões para observar um conflito

Onde executar · duas conexões com o mesmo servidor MySQL e o mesmo esquema.

Usaremos a sala 2 no dia 20/11/2026 às 15:00. Se a reserva já existir, escolha um horário livre e use a mesma combinação nos dois INSERT e na consulta final.

1. Mantenha a conexão atual como A. No Workbench, abra Database → Connect to Database…, selecione a conexão do laboratório em Stored Connection e confirme para abrir a sessão B. As abas de consulta de uma mesma conexão compartilham a sessão. Execute o bloco em A e B.

SQL · identificar cada conexão
USE pratica_salas;
SELECT CONNECTION_ID() AS sessao, DATABASE() AS banco;

Os números de sessao precisam ser diferentes e a coluna banco precisa indicar o mesmo esquema nas duas conexões.

2. Na sessão A, execute o bloco e deixe a transação aberta.

Sessão A · inserir e manter a transação aberta
START TRANSACTION;

INSERT INTO reserva (id_sala, id_usuario, data_reserva, hora_inicio, finalidade)
VALUES (2, 1, '2026-11-20', '15:00:00', 'Solicitação A');

3. Na sessão B, tente reservar o mesmo horário para outro usuário.

Sessão B · tentar a mesma reserva
START TRANSACTION;

INSERT INTO reserva (id_sala, id_usuario, data_reserva, hora_inicio, finalidade)
VALUES (2, 2, '2026-11-20', '15:00:00', 'Solicitação B');

B fica aguardando o desfecho de A porque os dois comandos disputam a mesma chave no índice uq_sala_horario.

4. Assim que B estiver aguardando, volte à sessão A e confirme.

Sessão A · confirmar
COMMIT;

5. Na sessão B, confira o erro 1062 (Duplicate entry) no Action Output e encerre a transação.

Sessão B · encerrar após a rejeição
ROLLBACK;

6. Em qualquer sessão, confira qual reserva foi registrada.

SQL · conferir a reserva final
SELECT id_reserva, id_usuario, id_sala, data_reserva, hora_inicio
FROM reserva
WHERE id_sala = 2
  AND data_reserva = '2026-11-20'
  AND hora_inicio = '15:00:00';

Confira antes de avançar

Deve aparecer uma reserva para o usuário 1, que fez o pedido na sessão A. Com o teste realizado uma vez, o esquema passa de quatro para cinco reservas.

10

Consultar o mesmo banco pela aplicação

Onde executar: terminal da aplicação Python; use o Workbench apenas para comparar.

1. No menu do programa, digite 1 e pressione Enter. Devem aparecer as 4 salas cadastradas, seus blocos e capacidades.

2. Digite 2 e pressione Enter. Devem aparecer 3 usuários.

3. Digite 3. Devem aparecer as reservas cadastradas até aqui: 5 se você realizou o teste com duas sessões da etapa 8, ou 4 se o pulou.

4. Volte ao Workbench, abra o editor SQL de pratica_salas e execute:

Workbench · conferir as reservas
SELECT COUNT(*) AS total
FROM reserva;

O número de registros deve ser igual ao exibido pela aplicação.

5. Abra o arquivo app_salas.py no editor de sua preferência e encontre a função listar_reservas(). Observe o trecho responsável pela consulta:

Python · trecho da aplicação
with conectar() as conn, conn.cursor() as cur:
    cur.execute("""
        SELECT r.id_reserva, r.data_reserva,
               TIME_FORMAT(r.hora_inicio, '%H:%i') AS hora,
               s.nome, u.nome, r.finalidade
        FROM reserva AS r
        JOIN sala AS s ON s.id_sala = r.id_sala
        JOIN usuario AS u ON u.id_usuario = r.id_usuario
        ORDER BY r.data_reserva, r.hora_inicio, r.id_reserva
    """)
    linhas = cur.fetchall()

O método execute() envia a SQL ao MySQL. fetchall() obtém as linhas retornadas, e TIME_FORMAT apresenta a hora como HH:MM.

Confira antes de avançar

Compare a contagem de reservas nos dois clientes. Ambos consultam o mesmo esquema pratica_salas.

Onde executar: terminal da aplicação Python e, no final, editor SQL do Workbench.

Solicitação do programaO que digitar

ID da sala4

Ao confirmar, o programa deve mostrar “Reserva confirmada” com um identificador gerado pelo MySQL.

4. Volte ao Workbench e confira as reservas da sala 4 nessa data:

Workbench · verificar a reserva criada

       s.nome AS sala, u.nome AS solicitante, r.finalidade

JOIN usuario AS u ON u.id_usuario = r.id_usuario

5. No arquivo app_salas.py, localize def criar_reserva(): e observe como a aplicação envia valores para o SQL:

Python · passagem de parâmetros
cur.execute("""
    INSERT INTO reserva
        (id_usuario, id_sala, data_reserva, hora_inicio, finalidade)
    VALUES (%s, %s, %s, %s, %s)
""", (id_usuario, id_sala, data, hora, finalidade))
identificador = cur.lastrowid
conn.commit()

O driver associa os valores da tupla aos marcadores %s. O cursor obtém o ID gerado em lastrowid, e commit() confirma a gravação. Se a inserção falhar, o programa executa rollback() e interpreta o erro.

Confira antes de avançar
