Preparação para a prática

Este material é um roteiro de execução. Você utilizará primeiro o pgAdmin para criar e consultar tabelas, observará mecanismos do PostgreSQL e, ao final, executará uma aplicação Python conectada ao mesmo banco.

Parte 1 · pgAdmin

Conferir a conexão, criar um banco próprio, construir quatro tabelas e cadastrar registros iniciais.

Parte 2 · Recursos do SGBD

Consultas, restrições, transações, índices e dois acessos simultâneos.

Parte 3 · Python

Preparar os arquivos, conectar com psycopg, consultar registros e testar novas reservas.

Tempo de referência

Três blocos de aproximadamente 30, 50 e 50 minutos. Prossiga somente após conferir o resultado de cada etapa.

03

Criar as tabelas e inserir os primeiros registros

Onde executar: Query Tool do banco pratica_salas. Você criará as tabelas bloco, sala, usuario e reserva, nesta ordem.

bloco1 → Nsala1 → NreservaN ← 1usuario

1. Abra uma nova consulta e crie a tabela bloco. Observe que id_bloco será preenchido automaticamente pelo PostgreSQL.

pgAdmin · SQL · tabela bloco
CREATE TABLE bloco (
    id_bloco INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nome_bloco VARCHAR(60) NOT NULL UNIQUE
);

2. Crie a tabela sala. O campo id_bloco faz a ligação com a tabela anterior. A restrição CHECK permite capacidades entre 1 e 80.

pgAdmin · SQL · tabela sala
CREATE TABLE sala (
    id_sala INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    id_bloco INTEGER NOT NULL REFERENCES bloco (id_bloco),
    nome VARCHAR(60) NOT NULL,
    capacidade INTEGER NOT NULL CHECK (capacidade BETWEEN 1 AND 80),
    ativa BOOLEAN NOT NULL DEFAULT TRUE,
    CONSTRAINT uq_sala_bloco UNIQUE (id_bloco, nome)
);

3. Crie usuario. O UNIQUE evita dois registros com o mesmo e-mail.

pgAdmin · SQL · tabela usuario
CREATE TABLE usuario (
    id_usuario INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    email VARCHAR(120) NOT NULL UNIQUE
);

4. Crie reserva. Cada registro apontará para uma sala e um usuário. O sistema considerará horários de uma hora, começando em hora cheia entre 08:00 e 21:00.

pgAdmin · SQL · tabela reserva
CREATE TABLE reserva (
    id_reserva INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    id_sala INTEGER NOT NULL REFERENCES sala (id_sala),
    id_usuario INTEGER NOT NULL REFERENCES usuario (id_usuario),
    data_reserva DATE NOT NULL,
    hora_inicio TIME NOT NULL,
    finalidade VARCHAR(160) NOT NULL,
    criado_em TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT ck_reserva_hora CHECK (
        hora_inicio >= TIME '08:00'
        AND hora_inicio < TIME '22:00'
        AND EXTRACT(MINUTE FROM hora_inicio) = 0
        AND EXTRACT(SECOND FROM hora_inicio) = 0
    ),
    CONSTRAINT uq_sala_horario UNIQUE (id_sala, data_reserva, hora_inicio)
);

5. No painel lateral do pgAdmin, clique com o botão direito em Schemas → public → Tables → Refresh. Confira se as quatro tabelas aparecem. Depois insira dois blocos e quatro salas:

pgAdmin · SQL · inserir blocos e salas
INSERT INTO bloco (nome_bloco)
VALUES ('Bloco A'), ('Bloco B');

INSERT INTO sala (id_bloco, nome, capacidade, ativa)
VALUES
    (1, 'Laboratório 101', 36, TRUE),
    (1, 'Sala 102', 45, TRUE),
    (2, 'Sala 201', 30, TRUE),
    (2, 'Laboratório 202', 24, TRUE);

6. Insira três usuários e quatro reservas iniciais:

pgAdmin · SQL · inserir usuários e reservas
INSERT INTO usuario (nome, email)
VALUES
    ('Ana Martins', 'ana.martins@exemplo.edu'),
    ('Bruno Costa', 'bruno.costa@exemplo.edu'),
    ('Carla Souza', 'carla.souza@exemplo.edu');

INSERT INTO reserva (id_sala, id_usuario, data_reserva, hora_inicio, finalidade)
VALUES
    (1, 1, DATE '2026-11-12', TIME '08:00', 'Aula de Banco de Dados'),
    (2, 2, DATE '2026-11-12', TIME '08:00', 'Projeto de Software'),
    (1, 3, DATE '2026-11-12', TIME '10:00', 'Monitoria'),
    (3, 2, DATE '2026-11-13', TIME '14:00', 'Reunião de projeto');

7. Conte os registros cadastrados:

pgAdmin · SQL · conferir a carga
SELECT
    (SELECT COUNT(*) FROM bloco) AS blocos,
    (SELECT COUNT(*) FROM sala) AS salas,
    (SELECT COUNT(*) FROM usuario) AS usuarios,
    (SELECT COUNT(*) FROM reserva) AS reservas;

Confira antes de avançar

O resultado deve ser 2 blocos, 4 salas, 3 usuários e 4 reservas. Se alguma instrução acusar relation already exists ou e-mail duplicado, não execute novamente a carga: ela pode já ter sido realizada. Use a consulta de contagem para verificar o estado atual.

Arquivo de apoio: baixar o SQL completo. O arquivo contém os mesmos comandos acima; não o execute novamente se já criou as tabelas e inseriu os dados manualmente.

2 · Como o SGBD garante consistência

Parte 2 · Observar o trabalho do SGBD 50 minutos

04

Consultar salas, reservas e estrutura das tabelas

Onde executar: Query Tool do banco pratica_salas.

1. Execute uma consulta que relacione cada sala ao seu bloco:

SQL · listar salas e blocos
SELECT s.id_sala, s.nome AS sala,
       b.nome_bloco AS bloco, s.capacidade
FROM sala AS s
JOIN bloco AS b ON b.id_bloco = s.id_bloco
ORDER BY s.id_sala;

Na aba Data Output, identifique a coluna bloco. Ela foi obtida da tabela bloco por meio do JOIN. O resultado deve ter 4 linhas.

2. Agora inclua WHERE antes de ORDER BY e consulte apenas salas com capacidade de pelo menos 30 lugares:

SQL · filtrar capacidade
SELECT s.nome AS sala, s.capacidade
FROM sala AS s
WHERE s.capacidade >= 30
ORDER BY s.nome;

O resultado deve mostrar 3 salas. O Laboratório 202 não aparece porque tem capacidade 24.

3. Execute uma consulta que combina três tabelas para mostrar as reservas iniciais:

SQL · reservas com nomes
SELECT r.data_reserva, r.hora_inicio,
       s.nome AS sala, u.nome AS solicitante, r.finalidade
FROM reserva AS r
JOIN sala AS s ON s.id_sala = r.id_sala
JOIN usuario AS u ON u.id_usuario = r.id_usuario
ORDER BY r.data_reserva, r.hora_inicio, s.nome;

Confira as 4 reservas. Os nomes das salas e dos usuários não estão gravados na tabela reserva; foram recuperados pelas chaves estrangeiras.

4. Por último, veja como o PostgreSQL descreve a própria tabela reserva:

SQL · metadados
SELECT column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'reserva'
ORDER BY ordinal_position;

Confira antes de avançar

A consulta de metadados deve listar as colunas da tabela reserva, como id_reserva, id_sala, id_usuario e hora_inicio. O information_schema mostra informações sobre as estruturas, não as reservas cadastradas.

05

Observar como o PostgreSQL rejeita dados inválidos

Onde executar: Query Tool. Cada tentativa abaixo é intencionalmente inválida. Execute os comandos separadamente e leia a mensagem na guia Messages.

Uma mensagem de erro é esperada. Não altere o comando para fazê-lo passar. Nesta etapa, a rejeição demonstra que as restrições funcionam. Se aparecer current transaction is aborted, execute ROLLBACK; em separado antes de continuar.

1. Teste de capacidade: tente cadastrar uma sala com capacidade negativa.

SQL · teste A · CHECK
INSERT INTO sala (id_bloco, nome, capacidade)
VALUES (1, 'Sala impossível', -5);

Observe a indicação de check constraint na mensagem. A tabela sala possui a condição capacidade BETWEEN 1 AND 80.

2. Teste de chave estrangeira: tente cadastrar uma reserva associada ao usuário 999, que não existe.

SQL · teste B · FOREIGN KEY
INSERT INTO reserva (id_sala, id_usuario, data_reserva, hora_inicio, finalidade)
VALUES (1, 999, DATE '2026-11-12', TIME '12:00', 'Teste de referência');

Observe a mensagem indicando que a chave não está presente na tabela usuario.

3. Teste de duplicidade: tente reservar a sala 1 no mesmo dia e horário de uma reserva já cadastrada.

SQL · teste C · UNIQUE
INSERT INTO reserva (id_sala, id_usuario, data_reserva, hora_inicio, finalidade)
VALUES (1, 2, DATE '2026-11-12', TIME '08:00', 'Reserva conflitante');

Observe a restrição uq_sala_horario, que impede repetir a combinação sala, data e horário.

4. Execute a consulta para conferir que nenhum dos testes inválidos criou registros:

SQL · conferir total
SELECT COUNT(*) AS total_reservas FROM reserva;

Confira antes de avançar

O total ainda deve ser 4 reservas. Os erros correspondem, na ordem, a CHECK, FOREIGN KEY e UNIQUE. Essas regras são verificadas pelo PostgreSQL, não pela interface do pgAdmin.

06

Desfazer e confirmar uma alteração

Onde executar: Query Tool, na mesma aba durante toda a etapa. Execute cada comando isoladamente, observando os valores antes de seguir.

1. Consulte a capacidade atual da sala 1:

SQL · valor inicial
SELECT id_sala, nome, capacidade
FROM sala WHERE id_sala = 1;

O valor inicial deve ser 36.

2. Inicie uma transação:

SQL · iniciar transação
BEGIN;

3. Altere temporariamente a capacidade para 50 e consulte novamente:

SQL · alterar e observar
UPDATE sala SET capacidade = 50 WHERE id_sala = 1;

SELECT capacidade FROM sala WHERE id_sala = 1;

O resultado na mesma sessão deve ser 50. Essa mudança ainda não foi confirmada.

4. Desfaça a alteração e consulte mais uma vez:

SQL · desfazer
ROLLBACK;

SELECT capacidade FROM sala WHERE id_sala = 1;

O valor deve voltar para 36.

5. Inicie uma nova transação, atualize a capacidade para 40 e confirme:

SQL · confirmar
BEGIN;
UPDATE sala SET capacidade = 40 WHERE id_sala = 1;
COMMIT;

SELECT capacidade FROM sala WHERE id_sala = 1;

Confira antes de avançar

A sequência observada deve ser 36 → 50 → 36 → 40. ROLLBACK desfez a alteração não confirmada; COMMIT confirmou a segunda alteração. Se executar tudo de uma só vez, você perde a oportunidade de observar os estados intermediários.

07

Visualizar índices, plano de execução e permissões

Onde executar: Query Tool do banco pratica_salas.

1. Descubra quais índices o PostgreSQL mantém para a tabela reserva:

SQL · consultar índices
SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'public'
  AND tablename = 'reserva'
ORDER BY indexname;

Localize o índice da chave primária e o associado à restrição uq_sala_horario.

2. Peça ao PostgreSQL para mostrar o plano que escolheria para localizar uma reserva específica:

SQL · observar plano
EXPLAIN
SELECT id_reserva, id_usuario
FROM reserva
WHERE id_sala = 1
  AND data_reserva = DATE '2026-11-12'
  AND hora_inicio = TIME '08:00';

Leia a primeira coluna do resultado. Ela pode indicar Seq Scan (varredura sequencial) ou Index Scan (acesso por índice). Com tão poucos registros, é normal o otimizador escolher Seq Scan.

3. Verifique o usuário conectado e seus privilégios básicos na tabela:

SQL · consultar permissões
SELECT current_user AS usuario_conectado,
       has_table_privilege(current_user, 'reserva', 'SELECT') AS pode_consultar,
       has_table_privilege(current_user, 'reserva', 'INSERT') AS pode_inserir;

Confira antes de avançar

Você deverá encontrar índices para PRIMARY KEY e UNIQUE. O EXPLAIN apresenta o plano estimado: ele não executa a consulta para recuperar as linhas. Os resultados de privilégios indicam o que o usuário atual está autorizado a fazer.

08

Usar duas sessões para observar um conflito

Onde executar: dois Query Tools do mesmo banco pratica_salas. Este teste precisa de duas conexões diferentes; identificaremos cada uma como A e B.

Antes de começar: esta demonstração deve ser feita uma única vez com a sala 2, no dia 20/11/2026, às 15:00. Caso você já tenha reservado esse horário, escolha outra combinação livre e use-a em ambas as sessões.

1. Abra duas abas independentes de Query Tool. Na primeira, escreva mentalmente “A”; na segunda, “B”. Em cada uma, execute:

SQL · identificar cada sessão
SELECT pg_backend_pid() AS minha_sessao;

Os números exibidos devem ser diferentes. Caso sejam iguais, abra um novo Query Tool que utilize outra conexão antes de continuar.

2. Na sessão A, execute o bloco abaixo. Não execute COMMIT ainda.

Sessão A · criar reserva sem confirmar
BEGIN;

INSERT INTO reserva (id_sala, id_usuario, data_reserva, hora_inicio, finalidade)
VALUES (2, 1, DATE '2026-11-20', TIME '15:00', 'Solicitação A');

3. Alterne para a sessão B e execute uma reserva para o mesmo horário, mas em nome de outro usuário:

Sessão B · tentar a mesma reserva
BEGIN;

INSERT INTO reserva (id_sala, id_usuario, data_reserva, hora_inicio, finalidade)
VALUES (2, 2, DATE '2026-11-20', TIME '15:00', 'Solicitação B');

O comando da sessão B poderá ficar aguardando. Isso é parte do teste: o PostgreSQL precisa saber se a primeira transação será confirmada ou desfeita.

4. Volte à sessão A e execute:

Sessão A · confirmar
COMMIT;

5. Na sessão B, verifique que a tentativa termina com erro de unicidade. Depois encerre a transação que falhou:

Sessão B · encerrar após a rejeição
ROLLBACK;

6. Em qualquer sessão, execute a consulta final:

SQL · conferir a reserva final
SELECT id_reserva, id_usuario, id_sala, data_reserva, hora_inicio
FROM reserva
WHERE id_sala = 2
  AND data_reserva = DATE '2026-11-20'
  AND hora_inicio = TIME '15:00';

Confira antes de avançar

O resultado deve ter apenas uma reserva, cadastrada pela sessão A. A restrição UNIQUE, combinada com o controle de concorrência do servidor, impediu duas gravações conflitantes. A partir desta etapa, o banco terá normalmente 5 reservas.

10

Consultar o mesmo banco pela aplicação

Onde executar: terminal da aplicação Python; use o pgAdmin apenas para comparar.

1. No menu do programa, digite 1 e pressione Enter. Devem aparecer as 4 salas cadastradas, seus blocos e capacidades.

2. Digite 2 e pressione Enter. Devem aparecer 3 usuários.

3. Digite 3. Devem aparecer as reservas cadastradas até aqui: 5 se você realizou o teste com duas sessões da etapa 8, ou 4 se o pulou.

4. Volte ao pgAdmin, abra o Query Tool de pratica_salas e execute:

pgAdmin · conferir as reservas
SELECT COUNT(*) AS total
FROM reserva;

O número de registros deve ser igual ao exibido pela aplicação.

5. Abra o arquivo app_salas.py no editor de sua preferência e encontre a função listar_reservas(). Observe o trecho responsável pela consulta:

Python · trecho da aplicação
with conectar() as conn:
    with conn.cursor() as cur:
        cur.execute("""
            SELECT r.id_reserva, r.data_reserva, r.hora_inicio,
                   s.nome, u.nome, r.finalidade
            FROM reserva AS r
            JOIN sala AS s ON s.id_sala = r.id_sala
            JOIN usuario AS u ON u.id_usuario = r.id_usuario
            ORDER BY r.data_reserva, r.hora_inicio, r.id_reserva
        """)
        linhas = cur.fetchall()

O método execute() envia a SQL ao PostgreSQL; fetchall() recebe as linhas retornadas. O código Python não lê diretamente os arquivos internos do banco.

Confira antes de avançar

Os registros consultados pelo Python e pelo pgAdmin são os mesmos, pois ambos utilizam o banco pratica_salas. A diferença está no cliente e na forma de apresentar o resultado, não no armazenamento.

11

Criar uma reserva pelo Python e conferir no pgAdmin

Onde executar: terminal da aplicação Python e, no final, Query Tool do pgAdmin.

1. Inserção válida. No menu da aplicação, digite 4 e preencha os campos um por vez:

Solicitação do programaO que digitar
ID do usuário1
ID da sala4
Data (AAAA-MM-DD)2026-11-21
Hora (HH:MM)09:00
FinalidadeEstudo em grupo

Ao confirmar, o programa deve mostrar “Reserva confirmada” com um identificador gerado pelo PostgreSQL.

2. Mesmo horário. Escolha novamente a opção 4, informe usuário 2 e mantenha sala 4, data 21/11/2026 e hora 09:00. Preencha uma finalidade qualquer.

O programa deverá informar “Horário indisponível” e não inserir um segundo registro. A aplicação usa ON CONFLICT ... DO NOTHING porque o PostgreSQL possui a restrição UNIQUE apropriada.

3. Horário inválido. Escolha a opção 4 novamente. Informe usuário 1, sala 4, a mesma data e hora 09:30.

A aplicação deverá mostrar que a reserva foi rejeitada: a restrição CHECK aceita apenas horários de início em hora cheia.

4. Volte ao pgAdmin e confira as reservas da sala 4 nessa data:

pgAdmin · verificar a reserva criada
SELECT r.id_reserva, r.data_reserva, r.hora_inicio,
       s.nome AS sala, u.nome AS solicitante, r.finalidade
FROM reserva AS r
JOIN sala AS s ON s.id_sala = r.id_sala
JOIN usuario AS u ON u.id_usuario = r.id_usuario
WHERE r.id_sala = 4
  AND r.data_reserva = DATE '2026-11-21';

5. No arquivo app_salas.py, localize def criar_reserva(): e observe como a aplicação envia valores para o SQL:

Python · passagem de parâmetros
cur.execute("""
    INSERT INTO reserva
        (id_usuario, id_sala, data_reserva, hora_inicio, finalidade)
    VALUES (%s, %s, %s, %s, %s)
    ON CONFLICT (id_sala, data_reserva, hora_inicio)
    DO NOTHING
    RETURNING id_reserva
""", (id_usuario, id_sala, data, hora, finalidade))
resultado = cur.fetchone()

Os marcadores %s recebem os valores enviados na tupla. A consulta permanece separada dos dados digitados pelo usuário.

Confira antes de avançar

A consulta no pgAdmin deve mostrar uma única reserva para a sala 4 em 21/11/2026 às 09:00. As duas tentativas seguintes não geram linhas. O PostgreSQL mantém as mesmas regras independentemente de o comando ter partido do pgAdmin ou do Python.

SintomaO que verificar

5 · Opcional

Conferir a persistência após reiniciar o servidor

Este procedimento é opcional e deve ser realizado somente após finalizar os testes anteriores.

  1. Feche a aplicação Python (opção 0) e volte ao PowerShell.
  2. Entre na pasta que contém o compose.yaml e execute docker compose stop.
  3. Reinicie o mesmo serviço com docker compose start.
  4. Abra novamente o pgAdmin e execute a consulta de contagem no banco pratica_salas.
PowerShell · parar e iniciar o PostgreSQL
Set-Location "$HOME\postgres-laboratorio"
docker compose stop
docker compose start
Não execute docker compose down -v. Esse comando pode remover o volume de dados utilizado neste laboratório.

Confira antes de avançar

Após reiniciar o contêiner, as tabelas e reservas devem continuar armazenadas. A persistência depende do volume configurado no tutorial; isso não substitui uma política de backup para recuperar exclusões acidentais.
