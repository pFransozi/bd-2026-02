PostgreSQL: do SGBD à aplicação

0 · Antes de começar

Contexto, objetivos e preparação

Situação-problema. A equipe de apoio de uma instituição precisa registrar salas, pessoas e reservas. Duas pessoas não podem usar a mesma sala no mesmo horário. Seu objetivo é descobrir como o PostgreSQL protege essas regras e depois verificar se as mesmas garantias continuam válidas quando uma aplicação Python solicita uma reserva.

PostgreSQL 18 + pgAdmin 4Python + psycopg 3≈ 130 minutosIndividual ou em dupla
Ao concluir, você deverá conseguir: identificar o cliente, o servidor e o banco; implementar tabelas e chaves; verificar restrições e transações; interpretar índices e concorrência; executar SQL a partir de uma aplicação.

Atenção: o tutorial anterior criou o banco laboratorio. Nesta prática será criado pratica_salas no mesmo PostgreSQL. Não apague o banco anterior nem remova o volume Docker.

pgAdmin (cliente)→ SQL →PostgreSQL (SGBD)← driver psycopg ←Aplicação Python

Regras do sistema que vamos construir

  1. Cada bloco possui várias salas.
  2. Cada reserva indica exatamente uma sala, um usuário, uma data e um horário.
  3. Uma reserva representa um intervalo de uma hora, com início em hora cheia, das 08h às 21h.
  4. A combinação sala + data + horário não pode se repetir.

Este é um modelo didático, não um sistema institucional completo. Regras como cancelamentos, conflitos entre intervalos de durações diferentes e verificação de sala inativa exigiriam decisões adicionais.

Como utilizar este roteiro (orientações para a execução)
  1. Leia o objetivo da etapa e, antes de rodar o SQL, tente prever o resultado.
  2. Execute os comandos no ambiente indicado: PowerShell, pgAdmin ou terminal Python.
  3. Compare o retorno com o quadro “O que conferir”. Um erro previsto em um teste de restrição é um resultado correto.
  4. Responda à pergunta final da etapa com base no que observou, não apenas na definição teórica.

No pgAdmin: conecte-se ao banco correto, abra Tools → Query Tool, selecione apenas o SQL que deseja executar e clique em ▶ (ou use F5). Em testes de transação, execute cada comando separadamente para observar os estados intermediários.

Parte 2 · Observar o trabalho do SGBD 50 minutos

04

Consultar dados e metadados

Conceito: a cláusula JOIN combina linhas de tabelas relacionadas; information_schema permite consultar a descrição dos objetos do banco, não os dados de negócio.

Onde executar: Query Tool do banco pratica_salas. Agora vamos recuperar informações relacionadas e examinar os metadados que o próprio PostgreSQL mantém.

Como ler as consultas

  1. Na primeira consulta, FROM sala AS s escolhe a tabela de origem.
  2. JOIN bloco AS b ON b.id_bloco = s.id_bloco encontra o bloco de cada sala.
  3. ORDER BY s.id_sala organiza a apresentação. Ele não altera a ordem física das linhas no banco.
  4. Na segunda consulta, observe que as informações do usuário e da sala vêm de tabelas diferentes.
SQL
SELECT s.id_sala, s.nome AS sala, b.nome_bloco AS bloco, s.capacidade
FROM sala AS s
JOIN bloco AS b ON b.id_bloco = s.id_bloco
ORDER BY s.id_sala;

Agora relacione reserva, sala e usuario para mostrar data, horário, sala, solicitante e finalidade.

SQL
SELECT r.data_reserva, r.hora_inicio,
       s.nome AS sala, u.nome AS solicitante, r.finalidade
FROM reserva AS r
JOIN sala AS s ON s.id_sala = r.id_sala
JOIN usuario AS u ON u.id_usuario = r.id_usuario
ORDER BY r.data_reserva, r.hora_inicio, s.nome;

Inspecione como o próprio SGBD descreve suas estruturas:

SQL
SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'reserva'
ORDER BY ordinal_position;

Sua vez · pequena alteração na consulta

Retorne à primeira consulta e adicione uma condição WHERE s.capacidade >= 30 antes do ORDER BY. Quantas salas permanecem? Explique por que Laboratório 202 não aparece.

O que conferir

A primeira consulta retorna 4 salas; a segunda retorna 4 reservas, inicialmente. Na terceira consulta, a coluna table_name deve mostrar reserva, e a listagem deve incluir id_reserva, id_sala e id_usuario.

05

Provocar três violações de integridade

Conceito: regras de integridade declaradas no esquema continuam valendo para qualquer cliente: pgAdmin, Python ou outro programa.

Onde executar: Query Tool. Você vai provocar três tentativas de inserção intencionalmente inválidas. O objetivo é entender qual regra do banco as impede.

Execute com atenção

  1. Leia cada tentativa e antecipe a regra que será violada.
  2. Execute somente uma instrução INSERT por vez, observe a aba de mensagens e anote a restrição indicada.
  3. Se surgir current transaction is aborted ao prosseguir, execute ROLLBACK; isoladamente para encerrar a transação com erro.
  4. Faça a consulta de contagem no final e compare com a contagem inicial.

06

Desfazer e confirmar alterações com transações

Conceito: BEGIN inicia uma transação; o que foi alterado nessa transação pode ser desfeito com ROLLBACK ou confirmado com COMMIT.

Onde executar: Query Tool. Vamos alterar temporariamente a capacidade de uma sala, verificar o valor e decidir entre desfazer (ROLLBACK) ou confirmar (COMMIT).

Execute cada linha separadamente

  1. Consulte a capacidade da sala 1: inicialmente deve ser 36.
  2. Execute BEGIN; e, depois, o UPDATE para 50.
  3. Execute o SELECT antes do ROLLBACK: na mesma sessão deve aparecer 50.
  4. Execute ROLLBACK; e consulte novamente: deve retornar para 36.
  5. Agora execute o segundo bloco, confirmando com COMMIT;. O novo valor deve permanecer em 40.

Selecione uma instrução de cada vez no editor. Executar o bloco inteiro sem observar os resultados intermediários reduz o valor do experimento.

Previsão

Se você atualizar para 50 e executar ROLLBACK, a sala fica com 50 ou 36 lugares? E depois de executar COMMIT, o que muda?

SQL · ROLLBACK
-- A: desfazer a mudança
SELECT capacidade FROM sala WHERE id_sala = 1;
BEGIN;
UPDATE sala SET capacidade = 50 WHERE id_sala = 1;
SELECT capacidade FROM sala WHERE id_sala = 1;
ROLLBACK;
SELECT capacidade FROM sala WHERE id_sala = 1;
SQL · COMMIT
-- B: confirmar a mudança
BEGIN;
UPDATE sala SET capacidade = 40 WHERE id_sala = 1;
COMMIT;
SELECT capacidade FROM sala WHERE id_sala = 1;

O que conferir

MomentoCapacidade da sala 1
Antes de alterar36
Dentro da transação, após UPDATE50
Após ROLLBACK36
Após a segunda alteração e COMMIT40

Uma transação enxerga as próprias alterações antes da confirmação. Isso não implica que outras sessões já possam observá-las.

Questão 6. Relacione o comportamento observado às propriedades de atomicidade e durabilidade (ACID). Por que uma consulta dentro da própria transação enxerga uma alteração ainda não confirmada?

07

Investigar índices e planejamento de consulta

Conceito: índices podem tornar algumas buscas mais eficientes. O planejador pode escolher entre varrer a tabela (Seq Scan) ou utilizar um índice (Index Scan), considerando o custo estimado.

Onde executar: Query Tool. Vamos inspecionar uma estrutura auxiliar usada pelo PostgreSQL e observar como ele decide executar uma consulta.

O que investigar

  1. Execute a consulta em pg_indexes e procure os índices gerados para a chave primária e para uq_sala_horario.
  2. Execute a consulta com EXPLAIN e procure o operador de acesso escolhido.
  3. Execute a consulta de privilégios e observe a identidade conectada.
SQL
SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'public' AND tablename = 'reserva'
ORDER BY indexname;
SQL
EXPLAIN
SELECT id_reserva, id_usuario
FROM reserva
WHERE id_sala = 1
  AND data_reserva = DATE '2026-11-12'
  AND hora_inicio = TIME '08:00';

Observação de segurança: verifique quem está conectado e quais privilégios essa identidade possui. No ambiente didático, o usuário aluno administra o banco; em produção, uma aplicação deveria receber somente os privilégios de que precisa.

SQL
SELECT current_user AS usuario_conectado,
       has_table_privilege(current_user, 'reserva', 'SELECT') AS pode_consultar,
       has_table_privilege(current_user, 'reserva', 'INSERT') AS pode_inserir;

O que conferir

O banco possui índices associados à PRIMARY KEY e à restrição UNIQUE. O plano pode mostrar Seq Scan porque existem pouquíssimas linhas: um índice disponível não significa que seja a melhor estratégia para toda consulta.

EXPLAIN sem ANALYZE mostra o plano estimado e não executa o SELECT para obter os registros.

08

Simular dois usuários tentando a mesma reserva

Conceito: um SELECT anterior pode indicar que um horário está livre, mas não o protege contra outra reserva inserida logo depois. A restrição UNIQUE deve continuar valendo sob concorrência.

Onde executar: duas janelas de Query Tool do mesmo banco, correspondentes a duas sessões diferentes. O objetivo é simular uma situação real: dois pedidos de reserva concorrentes.

Antes de iniciar: confira se o horário sala 2, 20/11/2026 às 15:00 ainda está livre. Não repita esse teste com a mesma combinação após concluí-lo: uma das sessões terá criado a reserva.

Organize as duas sessões

  1. Abra o Query Tool de pratica_salas em duas abas ou janelas separadas: A e B.
  2. Execute SELECT pg_backend_pid(); nas duas. Os números devem ser diferentes.
  3. Na sessão A, execute BEGIN; e o INSERT. Não execute COMMIT ainda.
  4. Na sessão B, execute também BEGIN; e tente o INSERT conflitante. Ele provavelmente ficará aguardando.
  5. Volte para A e execute COMMIT;. A instrução de B deve terminar com uma violação de unicidade.
  6. Em B, execute ROLLBACK; e só então faça o SELECT de conferência.
SQL · conexão A
BEGIN;
INSERT INTO reserva (id_sala, id_usuario, data_reserva, hora_inicio, finalidade)
VALUES (2, 1, DATE '2026-11-20', TIME '15:00', 'Solicitação A');
-- Não confirme ainda.
SQL · conexão B
BEGIN;
INSERT INTO reserva (id_sala, id_usuario, data_reserva, hora_inicio, finalidade)
VALUES (2, 2, DATE '2026-11-20', TIME '15:00', 'Solicitação B');
-- Aguarde o professor orientar a confirmação da conexão A.

Encerramento, sem misturar as sessões

Na sessão A: execute COMMIT;. Na sessão B: quando a tentativa falhar, execute ROLLBACK;. Depois execute a consulta abaixo em qualquer sessão.

SQL · conferir o resultado final (após A e B)
SELECT id_reserva, id_usuario, id_sala, data_reserva, hora_inicio
FROM reserva
WHERE id_sala = 2
  AND data_reserva = DATE '2026-11-20'
  AND hora_inicio = TIME '15:00';

O que conferir

Deve existir uma única reserva para aquela combinação. A segunda tentativa esperou a decisão da primeira e não conseguiu violar UNIQUE. Não foi o pgAdmin que resolveu o conflito; foi o PostgreSQL.

Questão 8. Por que consultar previamente se o horário está livre não é suficiente para impedir conflitos entre duas aplicações simultâneas? Identifique o papel da restrição de unicidade.

"""Aula 10: pequeno cliente de reservas com PostgreSQL e psycopg 3.

Pré-requisitos: executar 01_banco_salas.sql em pratica_salas e preparar .env.
"""

from datetime import date, time
from os import getenv

import psycopg
from dotenv import load_dotenv
from psycopg.errors import CheckViolation, ForeignKeyViolation

load_dotenv()


def conectar():
    """O driver abre uma conexão com o servidor PostgreSQL."""
    return psycopg.connect(
        host=getenv("PGHOST", "127.0.0.1"),
        port=int(getenv("PGPORT", "5432")),
        dbname=getenv("PGDATABASE", "pratica_salas"),
        user=getenv("PGUSER", "aluno"),
        password=getenv("PGPASSWORD"),
    )


def listar_salas():
    with conectar() as conn:
        with conn.cursor() as cur:
            cur.execute("""
                SELECT s.id_sala, b.nome_bloco, s.nome, s.capacidade
                FROM sala AS s
                JOIN bloco AS b ON b.id_bloco = s.id_bloco
                WHERE s.ativa = TRUE
                ORDER BY s.id_sala
            """)
            linhas = cur.fetchall()

    print("\nSALAS ATIVAS")
    for identificador, bloco, nome, capacidade in linhas:
        print(f"{identificador}: {nome} ({bloco}) - {capacidade} lugares")


def listar_usuarios():
    with conectar() as conn:
        with conn.cursor() as cur:
            cur.execute("SELECT id_usuario, nome FROM usuario ORDER BY id_usuario")
            linhas = cur.fetchall()

    print("\nUSUÁRIOS")
    for identificador, nome in linhas:
        print(f"{identificador}: {nome}")


def listar_reservas():
    with conectar() as conn:
        with conn.cursor() as cur:
            cur.execute("""
                SELECT r.id_reserva, r.data_reserva, r.hora_inicio,
                       s.nome, u.nome, r.finalidade
                FROM reserva AS r
                JOIN sala AS s ON s.id_sala = r.id_sala
                JOIN usuario AS u ON u.id_usuario = r.id_usuario
                ORDER BY r.data_reserva, r.hora_inicio, r.id_reserva
            """)
            linhas = cur.fetchall()

    print("\nRESERVAS CADASTRADAS")
    if not linhas:
        print("Nenhuma reserva cadastrada.")
    for identificador, data, hora, sala, usuario, finalidade in linhas:
        print(f"#{identificador} | {data} {hora:%H:%M} | {sala} | {usuario} | {finalidade}")


def criar_reserva():
    print("\nNOVA RESERVA (horários de 1 hora, em hora cheia)")
    try:
        id_usuario = int(input("ID do usuário: ").strip())
        id_sala = int(input("ID da sala: ").strip())
        data = date.fromisoformat(input("Data (AAAA-MM-DD): ").strip())
        hora = time.fromisoformat(input("Hora (HH:MM): ").strip())
        finalidade = input("Finalidade: ").strip()
        if not finalidade:
            print("Informe uma finalidade.")
            return
    except ValueError:
        print("Dados inválidos. Verifique os IDs, a data e a hora.")
        return

    try:
        with conectar() as conn:
            with conn.cursor() as cur:
                # %s e a tupla de valores evitam concatenar dados à SQL.
                cur.execute("""
                    INSERT INTO reserva
                        (id_usuario, id_sala, data_reserva, hora_inicio, finalidade)
                    VALUES (%s, %s, %s, %s, %s)
                    ON CONFLICT (id_sala, data_reserva, hora_inicio)
                    DO NOTHING
                    RETURNING id_reserva
                """, (id_usuario, id_sala, data, hora, finalidade))
                resultado = cur.fetchone()
        # Ao sair do `with` sem erro, psycopg confirma a transação.
        if resultado is None:
            print("Horário indisponível: a sala já está reservada nesse período.")
        else:
            print(f"Reserva confirmada. ID: {resultado[0]}")
    except ForeignKeyViolation:
        print("Reserva rejeitada: sala ou usuário inexistente (FOREIGN KEY).")
    except CheckViolation:
        print("Reserva rejeitada: use hora cheia entre 08:00 e 21:00 (CHECK).")


def main():
    while True:
        print("\n=== SISTEMA DE RESERVA DE SALAS ===")
        print("1 - Listar salas")
        print("2 - Listar usuários")
        print("3 - Listar reservas")
        print("4 - Criar reserva")
        print("0 - Sair")
        opcao = input("Opção: ").strip()
        if opcao == "0":
            print("Encerrado.")
            break
        try:
            if opcao == "1":
                listar_salas()
            elif opcao == "2":
                listar_usuarios()
            elif opcao == "3":
                listar_reservas()
            elif opcao == "4":
                criar_reserva()
            else:
                print("Escolha uma opção de 0 a 4.")
        except psycopg.Error as exc:
            print(f"Falha de banco de dados ({type(exc).__name__}).")
            print("Confira o servidor, o banco e as configurações do .env.")


if __name__ == "__main__":
    main()
